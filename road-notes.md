## 2026-10-06 — Разбор исходного плана: сверка с документацией

Исходный план (`docs/archive/2026-10-06-initial-plan.md`) сверен с актуальной
документацией goose (`/aaif-goose/goose`), `agent-client-protocol` Python SDK
(`/agentclientprotocol/python-sdk`) и Hermes Agent (`/nousresearch/hermes-agent`)
через Context7. На реальном Work Goose ничего не проверялось — это задача
`P0.2`.

Подтвердилось:

- `goose serve` отдаёт ACP по HTTP/WS на `/acp`; по умолчанию `127.0.0.1:3284`;
  auth — `X-Secret-Key` (`GOOSE_SERVER__SECRET_KEY`), для браузеров — `?token=`;
  `--tls` даёт self-signed сертификат и строку `GOOSED_CERT_FINGERPRINT=...`,
  Desktop пинит его или использует TOFU.
- Python SDK `acp` умеет быть клиентом через `create_http_stream` /
  `create_websocket_stream` + `connect_to_agent`; web-транспорты помечены
  experimental, Streamable HTTP требует HTTP/2, reconnect — забота вызывающего.
  Возможность передать свои заголовки и SSL-контекст в документации не найдена
  — открытый вопрос `P0.2`.
- Hermes подключает MCP-серверы по `url` + `headers` (есть `ssl_verify`,
  `timeout`, фильтр инструментов) и поддерживает плагины.

Отклонения от исходного плана и почему:

- **ACP-протокол руками не пишем** — берём SDK; `acp/protocol.py` и
  `acp/events.py` сводятся к обёртке (`goose/`).
- **Approval — входящий RPC-запрос `session/request_permission`**, а не
  методы `approve()/deny()` клиента. Approval Manager держит `Future`, ответ —
  выбранный `optionId`. `allow_always` из удалённых каналов запрещаем.
- **Streaming — базовый механизм, а не фаза 3**: `prompt()` возвращает только
  `stopReason`, текст идёт через `session/update`. Отдельной остаётся только
  UX-часть в Telegram.
- **Cancel — уведомление**, висящие permission-запросы закрываются `cancelled`.
- **`load_session` переигрывает историю** — при восстановлении подавлять.
- **Найден неучтённый риск**: если Bridge объявит client capabilities `fs` /
  `terminal`, рабочий агент сможет читать/писать файлы и выполнять команды на
  хосте Bridge. Добавлен инвариант «все capabilities выключены»
  (`docs/architecture.md`, §7).
- **Если Work Goose в режиме `auto`, approvals не приходят вовсе** — режим
  `approve`/`smart_approve` включён в `P0.1`, проверка — в `P0.2`.
- **BridgeCore — in-process ядро с первого дня**, каналы работают с ним
  напрямую; HTTP API — один из адаптеров, а не этап рефакторинга Telegram
  (бывшая Phase 6).
- **Hermes — через MCP-фасад, а не через собственный плагин**: Hermes
  нативно подключает MCP по URL, так дешевле и переиспользуемо. Из-за
  таймаутов MCP-вызовов введена модель jobs (`ask → job_id → result`).
- **Approvals уходят в канал-подтверждатель с человеком**, а не в исходный
  канал; MCP-канал не экспортирует approve/deny, чтобы LLM не подтверждал
  действия сам себе.
- Добавлены: обработка сообщения в занятую сессию (`SessionBusy`), несколько
  сессий на разговор (`/sessions`), таблица `approvals_audit`, стек без ORM,
  `uv`, aiogram 3, HTML parse mode в Telegram.

## 2026-10-06 — Решения владельца по топологии и порядку каналов

Вопросы и ответы:

- *Как домашний хост достучится до рабочего ноутбука?* — На старте обе машины
  в одной LAN; проблему доступа к `goose serve` в WSL решать сразу (`P0.1`).
  В будущем — исследовать стабильное соединение из любого места (`P4.1`).
- *Где работает Bridge?* — Bridge может оказаться на одной машине с Work
  Goose и быть просто шиной для внешних источников. Отсюда три топологии —
  LAN, co-located, anywhere (`docs/architecture.md`, §3); co-located
  поддерживается с MVP.
- *На какой платформе запускать Bridge?* — WSL — основной и рекомендуемый
  путь; Windows native — тоже; macOS — в будущем (`P3.1`, `P3.2`, `P4.6`).
  Следствие: ядро без OS-специфичных зависимостей, сервис-обёртки в
  `deploy/`.
- *Какой канал первый?* — Hermes, затем Telegram, затем возможны Snikket и
  Email, архитектура должна позволять добавлять другие каналы. Следствия:
  контракт канала в `P1.3`; CLI становится первым человеческим каналом и
  каналом подтверждений до Telegram; возник вопрос `P2.2`.

Следствие для сети: в топологии co-located spike `P0.2` можно делать по
loopback на рабочем ноутбуке, не дожидаясь `P0.1`.

## 2026-10-06 — Решения владельца: подтверждения, разговоры Hermes, имя проекта

- *`P2.1` — как ключевать разговор Hermes?* — Явным аргументом `thread` у
  MCP-инструментов, по умолчанию `default`.
- *Название пакета и CLI?* — Владелец предложил убрать «goose» из названия:
  механизм говорит на ACP и подходит не только для goose. Проект
  переименован в **ACP Gateway**: репозиторий и папка `acp-gateway`, пакет
  `acp_gateway`, CLI `acpgw`. Слово «gateway» владелец сам использовал для
  роли шины.

Следствия переименования для архитектуры (`docs/architecture.md`, §1 и §4.1):
`WorkGooseClient` → `AgentClient`; всё goose-специфичное (`X-Secret-Key`,
`GOOSED_CERT_FINGERPRINT`, режим подтверждений) ушло в профиль агента
`kind: goose`; в конфиге — список `agents:` (в MVP один профиль); MCP-
инструменты получили префикс алиаса агента (`work_ask` вместо
`work_goose_ask`). Ограничение, найденное при обобщении: почти все ACP-агенты,
кроме goose, говорят только по stdio, поэтому для них возможен лишь
co-located-запуск процессом — вынесено в `P4.7` (CONDITIONAL), чтобы не
усложнять MVP.

### Аналог: `acp-bridge` (xylophone21)

Имя `acp-bridge` на PyPI занято, поэтому проект посмотрели (2026-10-06):
<https://github.com/xylophone21/acp-bridge>, MIT, 1 звезда, 0 форков,
релизы 0.0.1–1.4.0 с 2026-03-31 по 2026-04-24, последний коммит 2026-09-20 —
живой, но фактически личный проект.

Что делает: связывает групповые чаты Feishu (Lark) с ACP-агентом, по умолчанию
Kiro CLI. Устройство: агент запускается **процессом по stdio на каждую сессию**
(`acp.spawn_agent_process`), сессии хранятся в памяти (LRU + TTL, без
персистентности), сообщения в занятую сессию ставятся в очередь, есть
опциональный «evaluator» — второй агент проверяет ответ перед отправкой.
Подтверждения — текстом в чат (номер варианта или `deny`), есть
`auto_approve`. Зависимости тяжёлые и прикладные (pandas, scipy,
matplotlib, `lark-oapi`).

Почему не форк и не зависимость: нет удалённого транспорта (только stdio), нет
персистентности сессий, единственный канал жёстко вшит (`feishu.py` ~28 КБ),
ядро не отделено от канала.

Что взять как референс: `acp_bridge/agent.py` — рабочий пример клиента на
`acp` SDK (`Client` с `session_update` / `request_permission`, ответы
`AllowedOutcome(option_id=...)` / `DeniedOutcome(outcome="cancelled")`, методы
`set_session_mode`, `set_config_option`); идея очереди сообщений в занятую
сессию (у нас пока `SessionBusy`, очередь — возможное улучшение); evaluator —
интересная идея на будущее, в план не вносится.

Проверка: `uv run pytest` — 80 passed; `ruff check`, `ruff format --check` —
чисто; хук прогнан вручную на проиндексированном дереве — чисто; `acpgw config

Решения и отклонения:

- **`.env` — только секреты, а не источник настроек.** Изначально `.env`
  планировался и для параметров. Отказались: при `extra="forbid"` dotenv-
  источник pydantic-settings считает лишними все ключи с префиксом `ACPGW_`
  (например `ACPGW_API_TOKEN`) и падает; кроме того, смешение секретов и
  параметров в одном файле путает. Настройки — `config.yaml` + переменные
  окружения `ACPGW_<РАЗДЕЛ>__<ПОЛЕ>`.
- **Секреты по ссылке.** Профиль агента хранит имя переменной
  (`secret_env`), значение читает `SecretStore` (окружение важнее `.env`) и
  отдаёт `SecretStr`; при загрузке значения регистрируются в маскировщике.
- **Инварианты закреплены в валидации конфига:** API только на loopback;
  нешифрованный транспорт к агенту только на loopback (иначе явный
  `allow_insecure_transport`); fingerprint — нормализованный SHA-256 и только с
  TLS; уникальные алиасы; неизвестные ключи — ошибка.
- **Маскирование логов — общий конвейер для structlog и stdlib**
  (`ProcessorFormatter` с `foreign_pre_chain`), чтобы секреты не утекали через
  сообщения сторонних библиотек (httpx, websockets). Маскируются значения
  чувствительных ключей, зарегистрированные секреты где угодно в строке,
  `token=` в URL, `Bearer ...`, `X-Secret-Key`. Исключения форматируются в текст
  до маскирования — тест `test_exception_text_is_redacted`.
- **Модуль назван `log.py`, а не `logging.py`** — чтобы не путать со
  стандартным модулем.
- **Свой сканер секретов вместо gitleaks/pre-commit.** gitleaks и
  pre-commit-фреймворк в окружении не установлены, а хук должен работать
  одинаково в WSL, Windows и macOS без лишних бинарников. Найдено и исправлено
  при разработке: первая версия правила «присвоенный секрет» ловила обычный
  Python-код (`token = _yaml_path.set(...)`) и не ловила секреты из одних
  букв из-за флага `(?i)` в проверке «ссылка на ALL_CAPS-переменную». Правило
  разделено на две формы — литерал в кавычках и целая строка `.env`/YAML, —
  проверка на ALL_CAPS сделана регистрозависимой; тест
  `test_repository_files_are_clean` гоняет сканер по всему репозиторию, чтобы
  ложные срабатывания всплывали сразу. Принятое ограничение: это эвристика, а
  не полноценный сканер; главная защита — `.gitignore` для `.env`,
  `config.yaml` и ключей плюс запрет этих имён в хуке.
- Пустые пакеты `agents/`, `core/`, `channels/` и т. д. не создавались —
  появятся вместе с кодом своих пунктов.

## 2026-10-06 — P0.2: spike-скрипт и находки по SDK `acp` 0.12.1

Добавлена зависимость `agent-client-protocol[http]` 0.12.1 (тянет `httpx[http2]`
и `websockets`), в dev — `uvicorn`. Написан `scripts/spike_acp.py`: сценарии
`tls`, `init`, `modes`, `ping`, `permission`, `cancel`, `load`, `all`; весь
JSON-RPC-трафик пишется в `spike-runs/<время>-<сценарий>-<транспорт>/traffic.jsonl`
(каталог в `.gitignore` — там могут быть рабочие данные), итоги — в
`summary.json`. Данные подключения берутся из обычного `config.yaml` + `.env`.

Находки по исходникам SDK (проверены чтением кода в `.venv`, не по докам):

- **`create_websocket_stream` не принимает SSL-контекст** (только `headers` и
  cookie store) — с самоподписанным сертификатом goose он не соединится, а
  пиннинг невозможен. Поэтому в spike свой `PinnedWebSocketTransport`
  (~30 строк, тот же протокол `Transport`). Это решает вопрос `P1.1`: WS-
  транспорт — свой.
- **`create_http_stream` принимает свой `httpx.AsyncClient`** — TLS-контекст
  передаётся через `verify=`, заголовок — через `headers=`.
- **Streamable HTTP ломает `session/load`**: и клиент, и эталонный сервер SDK
  привязывают сессию к соединению, только если в результате есть `sessionId`,
  а в `LoadSessionResponse` такого поля по схеме нет → prompt в загруженную
  сессию получает 404. По WS всё работает. Вывод: **основной транспорт — WS**;
  как поведёт себя HTTP у реального goose — проверить в прогоне.
- По умолчанию `ClientCapabilities()` уже объявляет `fs` и `terminal`
  выключенными; spike всё равно передаёт их явно, а методы fs/terminal на
  стороне клиента фиксируют вызов как нарушение.

Схема TLS-пиннинга (выбрана в spike, кандидат для `P1.1`): сначала сертификат
читается без доверия и без отправки учётных данных, сверяется SHA-256 с
`tls_fingerprint` из конфига либо с сохранённым TOFU-пином
(`<data_dir>/pins/<alias>.sha256`); затем строится SSL-контекст, доверяющий
только этому сертификату (`VERIFY_X509_PARTIAL_CHAIN`, без проверки имени
хоста), и уже в нём проходит рукопожатие с `X-Secret-Key`; после соединения
отпечаток сверяется ещё раз. Так секрет никогда не уходит MITM-узлу — тест
`test_tls_pin_mismatch_refuses_to_connect` проверяет, что до агента не дошло
ничего. Работает и с CA-, и с leaf-сертификатом (`CA:FALSE`) — какой
генерирует goose, неизвестно.

Фейковый агент `tests/fakes/fake_goose.py` (SDK `create_asgi_app` + uvicorn +
проверка `X-Secret-Key`, режимы `auto/approve/chat`, permission, cancel, load с
повтором истории) — заготовка для `P1.2`; после записи реального трафика mock
должен воспроизводить его, а не угадывать.

Проверка: `uv run pytest` — 92 passed (80 unit + 12 integration), `ruff
check` — чисто.

## 2026-10-06 — P0.2: прогон против реального Work Goose (goose 1.53.0)

Топология LAN: домашний ПК (WSL) → `https://<адрес-ноутбука>:3284`, TLS с
отпечатком из `GOOSED_CERT_FINGERPRINT` в `config.yaml`, секрет — в `.env`.
Доступ из LAN владелец уже открыл сам (`P0.1` фактически работает). Трафик —
`tests/fixtures/acp/goose-1.53.0/*.jsonl` (домашний путь заменён на
`/home/user`; секрета нет — проверено поиском значения по всем дампам).

Результаты (транспорт WS, если не сказано иное):

- **TLS.** `GOOSED_CERT_FINGERPRINT` = SHA-256 от DER сертификата — пин из
  конфига совпал с вычисленным; схема пиннинга из spike работает с
  сертификатом goose.
- **URL.** В конфиг владелец вписал базовый URL, как в Desktop
  (`https://…:3284`, без `/acp`). Spike теперь сам дописывает `/acp` при пустом
  пути и трактует `https` как `wss` — это же нужно в `P1.1`.
- **`initialize`.** `loadSession: true`, `sessionCapabilities: list, delete,
  close`, prompt: `image`, `embeddedContext`; MCP по HTTP; `authMethods:
  goose-provider` (вызывать не требуется — секрет уже аутентифицирует).
- **Режимы.** Новая сессия создаётся в **`auto`** (Desktop/сервер настроен
  так), режимы: `auto`, `approve`, `smart_approve`, `chat`; `set_mode`
  работает и шлёт `current_mode_update`. Вывод: Gateway обязан выставлять
  режим сам — иначе подтверждений не будет вообще.
  `configOptions`: `provider` (85 вариантов), `mode`, `model` (6),
  `thinking_effort` (5).
- **`ping`.** `stop_reason=end_turn`, текст `pong` одним `agent_message_chunk`;
  кроме него приходят `usage_update`, `session_info_update`,
  `available_commands_update`. Стоимость — ≈25 тыс. входных токенов на prompt.
  Ответ — 6 с.
- **Permission (режим `approve`, отказ).** `tool_call` →
  `request_permission` с 4 вариантами (`allow_always`, `allow_once`,
  `reject_once`, `reject_always`), `title` = `shell · <команда>`,
  `rawInput` = `{command, timeout_secs}`; на `reject_once` goose сообщил модели
  об отказе, команда не выполнилась, ответ `DENIED`. **Находка:** Work Goose
  переписал `sleep 30 && …` в `rtk sleep 30 && …` (его собственный хук RTK) —
  человеку надо показывать `rawInput`, а не исходную просьбу.
- **Cancel.** Работает на всех стадиях: во время генерации (через 5 с —
  `cancelled` за 0,01 с), при висящем `request_permission` (ответили
  `cancelled` — `cancelled` за 0,05 с), во время выполнения разрешённой
  команды (`cancelled` за 0,1 с). Убивает ли goose сам процесс команды — по
  трафику не видно (открытый вопрос, не блокирует).
- **`load`.** После разрыва и нового соединения `session/load` повторил
  историю (`user_message_chunk` + `agent_message_chunk`) до ответа на запрос;
  модель вспомнила кодовое слово.
- **Streamable HTTP.** `ping` работает, но `session/load` зависает: ответ
  уходит в session-scoped поток, который клиент SDK не открывает (нет
  `sessionId` в результате). Подтверждает выбор только WS.

## 2026-10-06 — P1.1, P1.2: AgentClient и mock-агент на записанном трафике

Сделано (`src/acp_gateway/agents/`): `AgentClient` поверх SDK `acp` 0.12 со

`wss`, пустой путь → `/acp` для goose); `acpgw config check` показывает оба.

Решения:

- **Подтверждения — через асинхронный обработчик**, который передаёт вызывающий
  (`permission_handler(PermissionRequest) -> option_id | None`). По умолчанию —
  `reject_all`. Маршрутизация к человеку — дело ядра (`P1.4`), клиент только
  гарантирует: неизвестный `option_id` или упавший обработчик → отказ;
  `cancel()` отвечает висящим запросам `cancelled`.
- **`prompt()` — асинхронный поток событий**, всегда заканчивается
  `TurnFinished`; если потребитель закрывает поток раньше — ход отменяется на
  агенте (иначе агент продолжал бы работать без получателя). Одна активная
  задача на сессию (`SessionBusy`).
- **Автозагрузка сессий.** Сессия, не привязанная к текущему соединению (после
  переподключения или в новом процессе), загружается через `session/load`
  перед prompt; повтор истории отбрасывается. Порядок гарантирован устройством
  SDK: уведомления, пришедшие до ответа, обрабатываются раньше него (проверено
  чтением `acp/connection.py`: входящие сообщения — задачи в порядке прихода,
  ответ будит ожидающего позже).
- **Повторные попытки** — `ensure_connected()` с паузами 1, 2, 5, 10, 30 с;
  ошибки аутентификации и пиннинга не повторяются.
- Для `kind: generic` секрет уходит как `Authorization: Bearer` (у goose —
  `X-Secret-Key`); проверено только для goose.
- Клиентские методы `fs/*`, `terminal/*`, `elicitation/*` отвечают «method not
  found» и пишут предупреждение, если агент их всё же вызовет.

## 2026-10-07 — P1.3: GatewayCore, хранилище, шина событий, контракт канала

Сделано: `src/acp_gateway/storage/` (SQLite, миграции, записи `Conversation`,
`SessionRecord`, `Job`), `src/acp_gateway/core/` (`GatewayCore`, `EventBus`,
ошибки ядра), `src/acp_gateway/channels/base.py` (контракт канала).

Решения:

- **Разговор = `(channel, key, agent)`**, а не `(channel, key)`: алиас агента
  входит в ключ, потому что MCP-инструменты Hermes и так префиксованы агентом
  (`work_ask`), а выбор агента в Telegram (`P4.7`) станет просто другим
  разговором. Сессия агента принадлежит ровно одному разговору
  (`UNIQUE (agent, acp_session_id)`); «подцепить» чужую сессию из Desktop
  пока нельзя — не просили.
- **`sqlite3` синхронно из event loop**, без `aiosqlite`: запросы трогают
  единицы строк локального файла, поток-посредник дороже. WAL, внешние ключи,
  миграции — пронумерованные `.sql` с `PRAGMA user_version`; каждая
  применяется в одной транзакции. Файл БД и каталог данных создаются с правами
  только владельца (`0600`/`0700`).
- **Хранится ответ, но не запрос.** Ответ нужен, чтобы `result(job_id)`
  пережил рестарт Gateway (Hermes может спросить результат позже); текст
  запроса не нужен никому. Готовые jobs удаляются через 7 дней (при старте
  ядра). Осознанный компромисс: ответы рабочего агента лежат на диске
  домашнего ПК до 7 дней — те же данные и так уходят в Telegram/Hermes.
- **Каждый prompt — job.** `submit` возвращает job сразу (сессия создаётся
  при первом сообщении разговора, под замком разговора — без гонки двух
  первых сообщений), `wait(job_id, timeout)` — финальный job или снимок с
  частичным ответом, `ask` = оба. Статусы: `running`, `completed` (любой
  `stop_reason`, кроме `cancelled`), `cancelled`, `failed` (ошибка агента),
  `interrupted` (Gateway остановился). Jobs, оставшиеся `running` после
  падения процесса, при старте помечаются `interrupted`.
- **Занятая сессия отклоняет новый запрос** (`SessionBusy`) уже в ядре, до
  обращения к агенту; другой разговор и `/new` в том же разговоре не
  блокируются. `cancel(conversation)` останавливает все jobs разговора, а не
  только активной сессии — иначе после `/new` старая задача была бы
  недоступна для `/stop`.
- **Агент не подтвердил отмену** (завис) — через 10 с ядро перестаёт ждать:
  отменяет задачу job, закрытие потока событий ещё раз шлёт `session/cancel`;
  job → `cancelled` с пояснением, сессия освобождается.
- **Шина** не блокирует ход: у подписчика ограниченная очередь, при
  переполнении события теряются со счётчиком и предупреждением в логе.
  События: `SessionCreated`, `JobStarted`, `JobProgress` (сырые события
  агента), `JobFinished`. Название сессии берётся из `session_info_update`.
- **Ядро владеет хранилищем и клиентами агентов** и закрывает их в `close()`;
  каналы регистрируются в ядре, ядро их запускает и останавливает (падение
  `stop()` одного канала не срывает остановку).

Найдено попутно:

- настоящий goose после первого ответа присылает `session_info_update` с
  названием сессии (`"Pong"`), mock этого не делал — добавлено из записи
  `ping.jsonl`;
- при ревью: задача job, отменённая в `close()` до своего первого шага, не
  выполняет ни строчки тела (и его `finally`) — job оставался `running`, а
  `wait()` висел вечно. `close()` теперь добивает такие jobs как
  `interrupted`; тест `test_shutdown_right_after_submit_settles_the_job` без
  исправления падает (проверено).

Не вошло (по плану — в другие пункты): лимиты `max_prompt_length` /
`max_response_length`, `allow_new_sessions`, `allow_cancel` и маршрутизация
подтверждений — `P1.4`; сборка ядра из конфига и запуск демона — `P1.5`.

Итог: `P1.3` — READY. `uv run pytest` — 247 passed (+41: 21 unit на
хранилище и шину, 20 интеграционных на ядро против mock-агента), `ruff check`
и `ruff format --check` — чисто; `tests/integration/test_gateway_core.py`
прогнан 30 раз подряд на итоговом коде — 0 сбоев. На реальном Work Goose ядро не
гонялось (поверх уже проверенного `AgentClient`; проверка целиком — в

## 2026-10-07 — P1.4: Approval Manager, аудит и политика

Сделано: `core/approvals.py`, `core/policy.py`, публичный метод
`AgentClient.set_permission_handler`, расширение контракта каналов и шины,
миграция `0002_approvals_audit.sql`, применение политики в `GatewayCore`.

Решения:

- **Ядро устанавливает свой обработчик на готовые клиенты.** Публичный setter
  можно вызвать только без активных turns/permissions/load. Вариант с созданием
  клиентов из конфига остаётся компоновкой `P1.5`, не обязанностью клиента.
  Внешний обработчик, переданный при создании клиента, не обходит политику ядра.
- **Подтверждение принадлежит job и агентской сессии.** Future хранится только
  в памяти; адресные `ApprovalRequested` идут подключённым человеческим каналам
  из allowlist, `ApprovalResolved` сообщает результат. Адаптер ставит
  `can_approve=True`, сообщает реальную доступность человека в `connected`,
  аутентифицирует его и передаёт actor в `resolve_approval`. Ядро повторно
  проверяет канал, адресацию, optionId и монотонный deadline. MCP/Hermes не
  могут подтверждать даже при ошибочной allowlist.
- **Первая терминальная операция выигрывает.** Повторное решение, чужой канал
  и просроченный запрос отвергаются. Таймаут, отсутствие человека и выключенные
  approvals дают `reject_once` (если агент предлагает), иначе `cancelled`.
  Причина автоматического отказа попадает в `job.error` вместе с ответом агента.
  Отмена job и остановка ядра закрывают pending-запросы; после рестарта они
  не восстанавливаются.
- **По умолчанию только `allow_once`/`reject_once`.** `allow_always` запрещён
  удалённым каналам всегда; локальному CLI доступен только при явном
  `allow_always_approval: true`. Каждый адресат получает только свои разрешённые
  варианты; копия аргументов в событии не позволяет изменить будущий аудит.
- **Решение записывается до ответа «allow».** `approvals_audit` содержит
  исходный разговор, job, инструмент и аргументы, время, исход, канал и actor;
  секреты и чувствительные ключи маскируются. Если запись не удалась, разрешение
  не отправляется. Аудит переживает рестарт и удаление старых jobs (`job_id`
  становится NULL); отдельная политика хранения аудита пока не введена.
- **Политика действует в ядре.** Длина запроса проверяется до обращения к
  агенту; `allow_new_sessions` запрещает также неявное создание, существующие
  сессии доступны. Ответ ограничен суммарно по чанкам: превышение сохраняет и
  публикует только допустимый префикс, закрывает ход и завершает job как failed.
  Пользовательская отмена учитывает `allow_cancel`, shutdown и защитная очистка
  обходят этот запрет. Проверки файлов готовы для будущих адаптеров; сам перенос
  файлов остаётся в `P4`.

Найдено при проверке: старый тест потерянной отмены ждал `tool_call`, который
приходит **до** подтверждения. После подключения менеджера это проверяло отмену
pending-approval, а не выполняющейся команды. Тест теперь явно ждёт отправки
решения simulated-human; сценарий потерянной отмены снова проверяет grace period.
Отмена job сразу после submit не отправляет prompt, если задача ещё не начала
работу. Повторный `close()` безопасен.

- **API владельца отделён от MCP и агента.** Обязателен собственный bearer-токен,
  отличный от настроенных агентских секретов и MCP-токена. Loopback binding и
  Host проверяются отдельно; тело ограничено до JSON parsing; ответы имеют
  `Cache-Control: no-store`. Ошибки валидации не повторяют ввод пользователя,
  внутренние ошибки не выдают traceback клиенту. OpenAPI/docs выключены.
- **Human CLI — живой watcher.** `approvals watch` устанавливает SSE-соединение
  с серверной случайной lease; её закрытие отзывает доступ к решению. Ни работа
  демона, ни список approvals не означают присутствия человека. Actor назначает
  сервер (`local-api-owner`), а не HTTP body. Несколько watchers допустимы;
  одноразовые `approve/reject` подтверждают существующий pending-запрос.
- **Streaming с восстановлением.** Job SSE начинается со snapshot; отдельный
  тип события отличает message от thought. При переполнении очереди старые
  chunks отбрасываются до resync, чтобы CLI не дописывал их после снимка.
  Завершённая job выдаётся целиком и закрывает поток. Отключение читателя не
  отменяет job; `result` позволяет восстановить ответ. Ctrl+C в `ask` посылает
  cancel. JSON-режим выводит только итоговый объект.
- **Адресная сессия без гонки переключения.** API проверяет принадлежность row
  id разговору, ядро выбирает явный ACP session id внутри conversation lock.
  Такой prompt не изменяет активный указатель и не зависит от параллельного switch.

Найдено при проверках: после отправки running-resync job могла завершиться,
а генератор проверял уже новое состояние и закрывался без финального ответа.
Проверка теперь относится к отправленному снимку; последующий JobFinished
доходит до читателя. Unicode line separators экранируются внутри JSON SSE,
иначе HTTPX `iter_lines` разделяет полезную нагрузку. IPv6 host в квадратных
скобках нормализуется для socket binding. Таймаут остановки тестового стенда
учитывает HTTP draining и стандартный 10-секундный WebSocket close handshake;
один teardown при параллельных прогонах вышел за старый предел 10 секунд,
отдельный повтор прошёл.

Проверка на **реальном Work Goose**: отдельный процесс `acpgw serve`, временные
owner token и БД; два CLI-хода сохранили одну ACP-сессию и кодовое слово
AMBERPINE. Интерактивный `approvals watch` отклонил запрос безвредного echo;
job завершилась, в SQLite подтверждены actor `local-api-owner`, outcome
`rejected`, option `reject_once`. Список сессий и итоговый `result` получены

Компьютеры устанавливают исходящее WSS-соединение при включении и возвращаются
после сна, выключения и потери сети. Один коннектор может представлять несколько

Агенты выполняют работу локально, сервер маршрутизирует запросы, ответы,
сессии и человеческие подтверждения. Через VPS проходят тексты и данные
approvals, рабочие файлы и credentials инструментов остаются на компьютерах.

Целевой агент — любой ACP-совместимый агент. Goose и Hermes используются как
кандидаты для проверки; реализация не должна требовать их наличия или
зашивать их особенности в общий контракт. Поддержка возможностей определяется
ACP capabilities; нужны локальный сетевой транспорт и мост к stdio. Hermes
как целевой ACP-агент здесь — отдельная роль от Hermes как MCP-канала `P2.1`.

## 2026-10-08 — P4.1: ревью плана и архитектуры

Ревью `docs/items/connector.md`, §3.2 архитектуры и кода этапов 1–2. Направление
верное: исходящий WSS, свой протокол, отдельные ключи компьютеров, обязательная
проверка TLS, отказ offline-цели без очереди, запрет автоматического replay.
Код этапов 1–2 аккуратный. До ACP relay нужно принять решения, иначе переделка:

1. **Процессная модель.** `dispatcher` — отдельный процесс со своим lock и
   in-memory `active`, а core/каналы/approvals живут в `serve`. Relay требует,
   чтобы core видел online-компьютеры и писал в их соединения. Рекомендация:
   ingress — компонент демона (второй listener в `serve` по секции конфига),
   отдельная команда — только для диагностики; иначе нужен IPC.
2. **Протокол relay.** Рекомендация: прозрачный ACP JSON-RPC в мультиплексном
   конверте `(alias, stream)`; на VPS — существующий `AgentClient` поверх
   `RelayTransport` (сейчас `PinnedWebSocketTransport` зашит в `client.py`,
   нужна инъекция транспорта). Так переиспользуются load/approvals/cancel/карантин,
   а approvals остаются штатным `session/request_permission`.
3. **Локальная политика коннектора (безопасность).** Полностью прозрачный
   коннектор позволит VPS (скомпрометированному или с ошибкой) прислать
   `session/new` с `mcpServers` (stdio-команда — запуск процесса агентом без
   approvals), произвольный `cwd` или `clientCapabilities` fs/terminal.
   Коннектор должен принудительно ставить `mcpServers: []`, ограничивать `cwd`
   локальными корнями, держать allowlist ACP-методов и выключенные capabilities.
4. **Размер кадров и flow control.** Control frame 64 KiB, агентский транспорт
   64 MiB; `session/load` replay и diffs tool_call не влезут в 64 KiB. Нужен
   отдельный лимит data-кадров и ограничение очереди на поток.
5. **Heartbeat.** Прикладной ping/pong в том же упорядоченном потоке, а цикл
   `handle` сам владеет `recv()`. С relay большой кадр задержит pong (ложный
   обрыв), а чтение придётся переписать в один demux-reader. Рекомендация:
   встроенный keepalive websockets (`ping_interval/ping_timeout`) + один reader.
6. **Повторное подключение.** «Второе соединение отклоняется» противоречит
   требованию переживать сон и смену сети: полуоткрытое старое TCP держит
   идентичность до ~2×heartbeat, а держатель украденного ключа может
   заблокировать легитимный компьютер. Рекомендация: newest-wins (новое
   аутентифицированное соединение вытесняет старое), epoch маркирует задачи,
   результаты/approvals старого epoch отвергаются.
7. **Модель TLS.** Pin сертификата ломается при каждом продлении Let's Encrypt
   (60–90 дней) для VPS с доменом. Варианты: CA + проверка имени при домене;
   SPKI-pin (ключ) с `--reuse-key`; текущий pin — для IP/self-signed. Плюс
   reverse proxy: сейчас listener требует TLS сам, нужен plaintext только на loopback.
8. **Адресация агентов в core.** Core и таблицы ключуются статическим alias
   из конфига. Нужны адрес `computer/alias`, динамическое появление/исчезновение,
   состояния online/ready и кадр статуса агента (manifest сейчас без готовности).
9. **Типизированные ошибки коннектора.** `connect_control` сводит всё в один
   `ValueError`; автоматический reconnect не отличит фатальные 401/pin от сетевых.
10. Проверка доступа опрашивает SQLite раз в секунду на соединение; в демоне
    отзыв может уведомлять напрямую, иначе один `PRAGMA data_version` на всех.
11. Граница доверия: компрометация VPS = одобрение любых действий на всех
    компьютерах. Это принятое допущение «trusted dispatcher» — стоит записать
    явно как принятый риск и оставить место для локальных ограничений (п. 3).
12. Публичный `/connect` без лимитов соединений/handshake — нужен reverse proxy
    или собственные лимиты к этапу 5.

Оценка 8–12 итераций выглядит оптимистичной: пп. 1, 2, 8 — рефакторинг ядра
до relay, этап 4 (recovery) остаётся главным риском. Рекомендуемый порядок:
решения пп. 1, 2, 6, 7 → инъекция транспорта и `RelayTransport` с одним
reader и keepalive → локальная политика коннектора → адресация `computer/alias`
с миграцией → relay одного агента end-to-end.

### 2026-10-13 — Финальный релиз позже; разные виды Hermes reconnect

По замечанию владельца финальная актуальная поставка перенесена после

не выполнялась.

По исходникам уточнено: local Hermes transport сейчас создаётся внутри remote
relay stream и закрывается при его завершении. Поэтому обычная потеря VPS WSS
теряет локальные handles даже при продолжающем работать Hermes. Это ограничение
нашей текущей архитектуры, а не доказательство невозможности продолжать чат
через Hermes. Рекомендован session manager в живом connector с независимым
lifetime attachment; новая remote epoch должна явно перепривязываться к trusted
локальной session, не принимать старые RPC и не повторять prompt.

Idle VPS reconnect, in-flight drop, потеря Hermes WS и cold restart Hermes
разделены в плане. Сохранение idle чата при живых connector/Hermes — реалистичная
локальная доработка. Гарантия при неизвестном исходе/потере всех локальных
состояний или cold resume требует отдельного контракта и проверки; текущие
запреты не сняты, код восстановления не реализован этим изменением.

## 2026-10-13 — P4.8 model control через managed stream, relay, core и owner API
