# Experimental managed Codex CLI

[Documentation](../README.md) · [P4.13 scope and evidence](../items/connector-harness-adapters.ru.md)

This is a source-checkout feature, not part of published ACP Gateway 0.2.2.
It starts a dedicated local `codex app-server --listen stdio://` process and
projects a restricted interface onto the existing gateway/connector transport.
It does **not** attach to Codex Desktop, import a CLI conversation or resume an
arbitrary native thread ID. Claude Code is not implemented by this adapter.
Running this adapter inside an explicit WSL distribution from a Windows
connector is described in [managed Codex/Claude inside WSL](windows-wsl-managed.md).

## Preconditions and interactive configuration

The current implementation targets the wire schema generated by Codex CLI
**0.163.0**. Initialize-only smoke checks use this version in WSL and native
Windows (Python 3.12.13). Live inference, Telegram and the complete native agent
lifecycle remain separate acceptance checks; see the startup-helper limitation below.
Use a separate test configuration and data directory rather than replacing a
working installation. See [development](../development.md) for the source
checkout and [gateway configuration](gateway.md) for explicit config/env paths.

Install and authenticate Codex separately on the agent computer using its normal
local workflow. The gateway does not install Codex, copy subscription credentials
to the dispatcher, or change the local account. A child inherits an allowlisted
environment (including local home/CODEX_HOME), not arbitrary gateway, Telegram,
provider-key or proxy environment variables. Configure supported credentials and
provider settings through Codex's own local configuration; do not put them here.

Use `acpgw setup` or `acpgw agents configure` with explicit test config/env paths.
Choose **codex** as the agent type, then its alias, project directory, local CLI
executable, optional model (`none` keeps the CLI default) and sandbox. Setup does
not install Codex or change its account. `read-only` is the default; enabling
`workspace-write` is an explicit choice. Editing preserves custom timeout values.
Missing executable advice points to PATH or a native absolute executable path.
The server's routed profile asks for computer/cwd, not a local executable.

Manual YAML remains available. Add this **local** profile under `agents` in a
separate test config, replacing paths with existing paths in the connector OS:

```yaml
agents:
  - alias: codex
    title: Codex CLI (experimental)
    kind: codex
    backend: codex
    default_cwd: /home/user/projects/test-project
    codex:
      executable: /home/user/.local/bin/codex
      sandbox: read-only
      request_timeout: 30
      turn_timeout: 600
      # model: an-explicit-model-id
```

Omitting `codex` uses the executable name `codex` from PATH and read-only defaults.
Only a local executable name or absolute executable path is accepted; no shell
command, arbitrary arguments, remote endpoint, agent secret or `session_mode`.
`default_cwd` must be absolute and is constrained by local agent policy. Native
Windows and WSL paths are not interchangeable. On Windows, use the native CLI's
absolute `codex.exe` path when it is not on PATH, not the Electron Desktop entry
point. The installed Desktop package's resources may deny direct execution;
setup does not modify WindowsApps permissions or install another binary silently.

The wizard can create, edit, keep, add or remove Codex profiles. Switching agent
kind removes incompatible transport/managed settings; duplicate addresses retry
before replacing the selected profile. Local and connector profiles retain local
Codex configuration; routed profiles keep credentials/executable settings off the
server. `agents install`, `agents serve` and `agents probe` do not gain Codex support;
use the ordinary configuration check and doctor instead:

```sh
uv run --frozen acpgw --config /path/to/test-config.yaml --env-file /path/to/test.env agents configure
uv run --frozen acpgw --config /path/to/test-config.yaml --env-file /path/to/test.env config check
uv run --frozen acpgw --config /path/to/test-config.yaml --env-file /path/to/test.env doctor
uv run --frozen acpgw --config /path/to/test-config.yaml --env-file /path/to/test.env doctor --live
```

Offline doctor starts no child. The Codex part of live doctor performs initialize
only and then closes its owned process: no thread or prompt. Other configured
components have their usual live probes; use a Codex-only test config when that
is the intended scope. Initialization does not prove account/model availability.

## Gateway and connector use

The profile can run in a local gateway or on an outgoing connector. Existing
connector enrollment and `computer/agent` addressing are reused; the local Codex
profile and credentials stay on the agent computer. Dispatcher and connector
must both run source that accepts `kind: codex`; an older dispatcher does not
acquire that support from a new connector alone. Do not replace a production
service for this experiment.

Use the existing session/new and prompt workflows in [the CLI](gateway.md) or
[Telegram](telegram.md). A new dedicated dialogue must be created explicitly;
its native identity is not a general-purpose attach token. Multiple completed
turns can use that same dialogue while its connection is alive. Automated tests
exercise the native subprocess peer and existing connector relay; a real model
and Telegram round trip still require separate acceptance.

## Approvals and failure boundaries

- Sandbox defaults to `read-only`; `workspace-write` is an explicit opt-in for
  the configured workspace, with tool network access disabled by that policy.
  A working-directory policy is not a sandbox for every upstream integration.
- The native approval policy is `untrusted`, with a human reviewer. Codex may
  execute actions permitted by its policy without requesting approval. This is
  not a promise of a new gateway confirmation for every tool call.
- Requested actions use the existing human approval manager: once-only allow or
  deny, no session/always grant. Foreign, unsupported or expired authority must
  not grant access. Keep a real authorized CLI/Telegram approver connected.
- Only matching thread/turn answer events become assistant output. Tool output,
  diagnostics and native stderr are not treated as the assistant's answer.
- Cancellation and session/load are explicitly unsupported. Closing an owned
  child is resource cleanup, not proof that all tool descendants stopped or that
  an action was undone. It does not terminate other CLI/Desktop applications.
- Disconnect, timeout or an uncertain outcome never resends the prompt and never
  resumes another thread implicitly. The old selected dialogue can become
  unavailable. Check that work really stopped before maintenance or explicitly
  creating a different dialogue; changing the selection is not recovery evidence.
- No model catalogue, automatic installer, Desktop integration or persisted owned
  resume is claimed. Native initialization and model-free subprocess tests are
  not a supported live-model Windows release.

### Native Windows startup-helper limitation

An isolated Codex 0.163.0 initialization can start its own `git.exe` helper. Scoped
Windows handle inspection reproduced that helper retaining the test working
directory after the immediate App Server exited, even with stdio handles closed
and its asyncio subprocess transport finished. A 300 ms graceful EOF experiment
let Codex exit with code 0 but did **not** remove the lock (five of five runs).
In this parent check the helper subsequently exited by itself, and the directory
became removable after about 1.75–1.84 seconds in four of five runs. Therefore, no unproven grace-period
patch or process-tree termination was added.

Do not interpret a successful initialize/closed-pipe result as proof that every
upstream helper has exited, and do not immediately delete or replace that agent's
working directory. Gateway stops only its owned immediate process. Complete
native lifecycle acceptance remains open pending an upstream contract or an
explicitly designed descendant-ownership policy; setup does not kill other Git,
CLI or Desktop processes.

## Automated checks without inference

```sh
uv run --frozen pytest tests/unit/test_codex_config.py tests/unit/test_codex_cli.py tests/integration/test_codex_managed.py tests/integration/test_codex_windows.py
uv run --frozen ruff check
uv run --frozen ruff format --check
```

Shared subprocess peer checks now run on POSIX and native Windows. The Windows
fixture replaces only executable launching with a real Python peer: JSONL codec,
Proactor pipes, permissions, relay and owned cleanup remain real. POSIX signal
checks are skipped on Windows; separate native handle tests cover inherited
pipes, a cancelled close caller and survival of unrelated processes. Tests do
not establish live model, provider, Desktop or complete upstream-helper support.
