## 2026-10-13 — общий бюджет запуска работы для каналов

В ядре реализован WorkRateLimiter: rolling window по monotonic clock,
по умолчанию 60 допущенных попыток new-session/submit за 60 секунд на канал.
CLI и owner API используют cli; MCP и Telegram имеют независимые бюджеты.
Внутри канала смена thread/agent/user не обходит лимит. Первая submit с
implicit session/new расходует один слот, public new_session — один.
Проверка и резервирование без await выполняются до conversation lock и
upstream/SQLite side effects. В памяти не более work_requests timestamps
на доверенное имя канала. Config копируется, env nesting поддержан.

RateLimited — безопасная пользовательская ошибка с integer retry_after.
Owner HTTP возвращает 429/Retry-After; CLI показывает ошибку, MCP isError
и Telegram используют существующую обработку GatewayError. Автоповтора
отвергнутого prompt нет. Result polling, cancel, approvals, health и
model control не расходуют этот бюджет. Неизвестный agent/policy-invalid
prompt отвергаются до admission; дальнейшие ошибки, включая busy/agent
unavailable, расходуют уже допущенную попытку. Это не persistent quota и
не ограничение общего числа активных jobs; restart сбрасывает окно.

Добавлены 9 cases: границы окна и округление retry, channels isolation,
bounds/env/settings copy, настоящий owner HTTP auth/429/no-store,
MCP ошибки и отсутствие побочных сессий, независимый CLI budget,
конкурентные threads (из 10 new-session при одном слоте проходит 1).
Первый targeted run выявил только ошибку новой фикстуры: server.url
требует scheme; исправлено на server.url("ws"), три новых integration
cases прошли повторно. Полный WSL source: **1175 passed / 28 skipped**,
152.28 s; JUnit /tmp/acpgw-p33-channel-limits.xml. Native Windows source:
**37 passed**, 9.62 s; JUnit
C:/Users/vladz/AppData/Local/Temp/acpgw-p33-channel-limits-native.xml.
Ruff check/format: 227 files clean.

Настройка описана в ../setup/rate-limits.md, config.example.yaml и

## 2026-10-13 — P2.3/P3.3/P3.6: durable delivery, status и проверки обновления

По просьбе владельца реализованы все три выбранных участка. Development
0.2.0rc2.dev0 использует новую миграцию 0008; frozen 0.2.0rc1/schema 6 и
его transfer archive не пересобирались. Wheel hash кандидата повторно совпал.

**Очередь ответов.** Plain-text Telegram submit передаёт доверенный bot namespace
в core; Store.add_job атомарно создаёт job и outbound reference. SQL trigger
делает waiting→pending в одной операции с terminal job status, включая startup
interruption. Worker читает SQLite при старте и по idle-интервалу, поэтому
доставка не зависит от сохранности bus event. Сохраняются ACK chunk cursor,
state, retry_at и digest redacted/rendered chunks; дополнительной копии ответа нет.
Namespace и known allowlisted chat проверяются перед отправкой. /delivery JOB_ID
показывает state/cursor только для owned conversation; /result остаётся явным
полным повторным получением через отдельную bounded ephemeral queue.

Каждая часть резервируется как sending до network call. Accepted ACK двигает
курсор; restart продолжает pending с оставшейся части. Vanished sender, network
ambiguity, потерянный локальный ACK commit и changed rendering дают unknown,
автоповтора нет. Явный 429 даёт delayed pending; BadRequest/Forbidden — failed.
Queue references удаляются с jobs по retention; backlog может истечь. Старые
programmatic submit без delivery_namespace сохраняют legacy event reply.
Agent prompts и pending approvals не восстанавливаются/не переигрываются.

**Status edits.** Отдельный worker редактирует исходный Working message:
до 1500 redacted answer characters, затем terminal status и /result. По умолчанию
интервал 2 s, bounds 1–60; status_enabled отключает edits. В памяти до 32 status
records. Unchanged text не отправляется; 429 откладывает edit того же message;
другие edit errors прекращают advisory status, не durable result delivery.
Worker независим от polling/approval/results. Старые status messages после
restart не rediscover; reasoning/tool arguments не пересылаются.

**Update/rollback.** Исправлено восстановление изначального отсутствия database,
если failed health новой версии успел создать SQLite. Важная граница:
snapshot rollback способен вернуть старый pending/ACK cursor после фактической
Telegram отправки; restore поэтому переводит waiting/pending/sending в unknown,
сохраняя ответ и cursor для /result. Definitive delivered не переигрывается.
Standard-library helper не требует импортов приложения для этого fence.

Добавлены 23 cases (5 storage, 14 Telegram delivery/status, 4 maintenance):
атомарные failure triggers job/outbox, ACK/restart, lost ACK, denied recipients,
hash mismatch, ручной /result, независимые status edits/429/partial redaction,
реальный crashed installer child с partial environment/entry/WAL mutation,
restore failure с сохранением snapshot, новая БД после failed health и queue/
selection recovery. Native tests выявили незакрытые SQLite handles в прежнем
стенде (sqlite context commits, но не closes) и недостающие PID/lease plan fields;
стенд исправлен без обхода Windows locks. Synthetic credential в новом
redaction test заменён runtime generation после срабатывания secrets scanner.
