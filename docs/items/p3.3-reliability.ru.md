## 2026-10-13 — P3.3: ограниченная периодическая SQLite retention

После передачи инструкции владельцу выполнен следующий независимый пункт очереди.
Версия разработки повышена до 0.2.0rc2.dev0, uv.lock обновлён offline; frozen
0.2.0rc1 wheel и внешний установочный архив не пересобирались. Их hashes проверены.

RetentionSettings передаётся из daemon в GatewayCore: jobs_days=7,
approval_audit_days=null (удаление аудита только по явной настройке),
sweep_interval_seconds=3600, batch_size=1000. Startup и фоновый task очищают
не более одной порции каждой таблицы; строгий timestamp cutoff сохраняет
пограничные и свежие записи. Миграция 0007 добавляет индексы; сама данные не
удаляет. Running jobs, sessions/bindings/model state и pending approvals не
затрагиваются. Job expiry обнуляет FK аудита, сохраняя решение до отдельного
audit cutoff. Ошибка sweep логируется без SQLite exception text; serve продолжает
работу, следующая попытка идёт по интервалу. Фоновый task отменяется/ожидается
до закрытия store. Автоматического VACUUM и удаления upstream истории нет.

14 новых cases проверяют batch/boundary/FK, запрет некорректных размеров,

## 2026-10-13 — общий бюджет запуска работы для каналов

В ядре реализован WorkRateLimiter: rolling window по monotonic clock,
по умолчанию 60 допущенных попыток new-session/submit за 60 секунд на канал.
CLI и owner API используют cli; MCP и Telegram имеют независимые бюджеты.
Внутри канала смена thread/agent/user не обходит лимит. Первая submit с
implicit session/new расходует один слот, public new_session — один.
Проверка и резервирование без await выполняются до conversation lock и
upstream/SQLite side effects. В памяти не более work_requests timestamps
на доверенное имя канала. Config копируется, env nesting поддержан.

RateLimited — безопасная пользовательская ошибка с integer retry_after.
Owner HTTP возвращает 429/Retry-After; CLI показывает ошибку, MCP isError
и Telegram используют существующую обработку GatewayError. Автоповтора
отвергнутого prompt нет. Result polling, cancel, approvals, health и
model control не расходуют этот бюджет. Неизвестный agent/policy-invalid
prompt отвергаются до admission; дальнейшие ошибки, включая busy/agent
unavailable, расходуют уже допущенную попытку. Это не persistent quota и
не ограничение общего числа активных jobs; restart сбрасывает окно.

Добавлены 9 cases: границы окна и округление retry, channels isolation,
bounds/env/settings copy, настоящий owner HTTP auth/429/no-store,
MCP ошибки и отсутствие побочных сессий, независимый CLI budget,
конкурентные threads (из 10 new-session при одном слоте проходит 1).
Первый targeted run выявил только ошибку новой фикстуры: server.url
требует scheme; исправлено на server.url("ws"), три новых integration
cases прошли повторно. Полный WSL source: **1175 passed / 28 skipped**,
152.28 s; JUnit /tmp/acpgw-p33-channel-limits.xml. Native Windows source:
**37 passed**, 9.62 s; JUnit
C:/Users/vladz/AppData/Local/Temp/acpgw-p33-channel-limits-native.xml.
Ruff check/format: 227 files clean.

Настройка описана в ../setup/rate-limits.md, config.example.yaml и
