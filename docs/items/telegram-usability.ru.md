# P2.4 — удобство Telegram: диалоги, подтверждения и ход работы

> сохраняют evidence, но больше не являются активной очередью.


**Статус:** PARTIAL — кодовая часть P2.4 реализована и проверена 2026-10-15:

**Основа:** существующие core sessions/jobs/approvals/outbox и

## 1. Диалоги

Осмысленные названия, агент и компьютер, последняя активность и понятное
состояние диалога. Кнопки «Открыть», «Новый» и «Переименовать».
Переход из истории задачи к её диалогу должен явно показывать выбранный маршрут.

Переименование нужно проектировать с учётом возможностей адаптера: название
диспетчера и заголовок Hermes могут иметь разные источники. Нельзя обещать
синхронизацию с Desktop без подтверждённого host RPC или перезаписывать ручное
название пользователя. Отсутствие поддержки должно отображаться понятно.

## 2. Подтверждения

Компактная карточка: какое действие запрошено, каким агентом/ПК, для какой задачи
и диалога; понятные аргументы вместо необработанного JSON там, где это возможно.
Полный ввод должен оставаться доступным для осознанного решения: краткое
представление не должно скрывать важную часть команды или её последствия.

Кнопки решения, переход к задаче, видимый итог после выбора и отключение
неактуальных кнопок. Сохраняются user/chat/message/request binding, срок действия,
once-only решение, аудит и различение originating channel. Повторный показ
не создаёт нового запроса и не разрешает действие автоматически.

## 3. Ход выполнения

Краткие этапы в одной обновляемой карточке: агент/ПК, диалог, длительность,
ожидание подтверждения, завершение или ошибка. Остановка — только при
поддержке безопасной отмены; запрос отмены не равен подтверждённой остановке.

Показывать только доступные события, без выдуманного процента готовности,
раскрытия внутренних рассуждений или полного сырого tool потока. Частоту и объём
обновлений ограничить; 429 и сбой редактирования не должны блокировать
подтверждения и доставку итогового ответа. Сохраняются outbox ACK/unknown fences.

## 4. Единый интерфейс и навигация

Согласованные русские подписи основных карточек и кнопок, короткие ошибки
с конкретным следующим действием. Возврат к предыдущему списку сохраняет
страницу и фильтр; выбранный агент/диалог виден без лишних сообщений.
Ответы, подтверждения и навигационные карточки сохраняют своё назначение.

Маршрут, пользователь и диалог проверяются при каждом действии; устаревшие
кнопки и поздние RPC-ответы не меняют более новый выбор.

## Предлагаемый порядок

1. Диалоги и подтверждения — основной ежедневный путь.
2. Карточка хода выполнения.
3. Общая навигация и согласование оставшихся подписей в затронутых экранах.

2026-10-15 владелец разрешил продолжение реализации и проверки без релизов.
Точный UX переименования и набора progress events уточняется по фактическим
возможностям core и адаптеров при начале работы.

## Критерии приёмки

- Пользователь выбирает диалог, узнаёт его назначение и возвращается к тому же
  месту списка; переименование не затрагивает чужие/невыбранные диалоги.
- По карточке подтверждения понятно, что будет выполнено и где; решение
  применяется ровно один раз, просроченные/чужие кнопки отказывают.
- Progress отражает фактическую работу и ожидания; итог доставляется независимо
  от отказов status edits. Отмена показывается по подтверждённому состоянию.
- На двух ПК параллельные задачи не смешивают маршрут, диалог, ответ и approval.
- Автоматические проверки покрывают privacy/stale/concurrency/delivery, затем
  владелец проводит живую Telegram-приёмку. Факт реализации и результаты
  записываются сюда при возвращении к P2.4.

### 2026-10-15 — предпросмотр диалога и сохранение страницы

Владелец возобновил трек улучшений Telegram для диспетчера и явно запретил
релизы. В списке диалогов найдено неудобство: нажатие строки сразу меняло
получателя следующих сообщений, а возврат из выбранного диалога всегда открывал
первую страницу.

Кнопка списка теперь открывает предпросмотр: сохранённое название, агент,
рабочая папка, известное состояние, последняя активность и явная отметка,
выбран ли диалог для сообщений. Предпросмотр не меняет active selection/revision
и не вызывает ACP. Выбор выполняется отдельной кнопкой; возврат до и после
выбора сохраняет исходный номер страницы. Текстовая команда `/dialogue ID [PAGE]`
открывает тот же предпросмотр, `/switch ID [PAGE]` сохраняет прямой выбор.

Обе команды проверяют принадлежность текущему private chat/channel/agent;
неверная страница отклоняется до изменения выбора. Кнопки предпросмотра привязаны
к маршруту, кнопка выбора — также к revision выбранного диалога и once-only.
Старые callbacks после редактирования панели недействительны. Полный путь через
настоящий aiogram dispatcher и fake Bot API проверяет возврат на вторую страницу,
отсутствие ACP prompts, изоляцию трёх чужих scopes и отказ устаревшего выбора.

Остаток P2.4: переименование с явным разграничением названия диспетчера/Hermes,
компактные полные по смыслу approvals, фактический progress и общие подписи.
Живая Telegram-приёмка этой итерации не выполнялась; публикации и production
обновления не выполнялись.

Проверки 2026-10-15: полный source suite **1348 passed / 35 skipped**,
195.585s; JUnit: `dist/telegram-usability-verification/source.xml`,
результат RTK: `dist/telegram-usability-verification/source.log`.
Telegram regressions (commands/controls/dashboard/delivery/format/panel guards)
пройдены перед полным прогоном. `ruff check src tests`,
`ruff format --check src tests` и `git diff --check` пройдены.
Native Windows для этой итерации не запускался.


### 2026-10-15 — завершение реализации P2.4 без релиза

Добавлено локальное название диспетчера: кнопка «Переименовать» объясняет
команду `/rename ID TITLE`. Явная команда проверяет chat/channel/agent ownership,
нормализует пробелы, принимает 1–120 печатных символов и не меняет выбранный
диалог. Название сохраняется в SQLite channel state отдельно от host title;
ключ включает conversation/id/created_at, чтобы возможное повторное использование
ID не переносило имя в другой диалог. Поздние SessionInfoUpdated не затирают
ручное имя диспетчера. Заголовок Hermes не меняется и синхронизация не обещается.

Карточка подтверждения показывает источник, agent/PC, job/dialogue и UTC deadline.
Сокращение ввода явно помечено; полный redacted JSON доступен по страницам,
без скрытого хвоста. Повторный показ не создаёт нового permission request.
Решение остаётся once-only, с прежними user/chat/message/request binding и аудитом.
После решения/таймаута все известные копии показывают итог и теряют кнопки.
При ошибке редактирования повторного решения не происходит: core уже settled,
binding удалён. Копия, отправлявшаяся одновременно с решением, после отправки
сверяет pending/audit и сразу становится неактивной. Кэш карточек ограничен 256.
Ссылка на задачу доступна только для исходного Telegram-чата; MCP approvals
сохраняют свой origin и не открывают чужую историю.

Рабочая карточка показывает фактический state, agent/PC, dialogue, длительность
и ожидание permission. Проценты и внутренние рассуждения не добавлены; preview —
только внешний answer. Сохранены отдельная status task, интервал и 429 backoff,
durable outbox ACK/unknown fences и независимость доставки результата.
Кнопки статуса заменяются только после успешного edit. Отмена показывается
по реальному состоянию core, при отсутствии capability кнопки отмены нет.

История задач сохраняет cursor/filter при переходах задача → доставка →
задача → история. Кнопка выбора диалога из задачи явно указывает agent/id,
проверяет job ownership и выбирает точный маршрут/диалог без ACP prompt;
повторный callback не меняет selection revision. Основные подписи диалогов,
подтверждений и рабочих карточек согласованы на русском.

Проверки покрывают полный длинный ввод, чужой private chat, once-only аудит,
гонку send/resolve, сохранность имени после повторного открытия SQLite и обновления
host title, ожидание approval и завершение, возврат фильтра/cursor и адресный
переход к диалогу. Релизы и production обновления не выполнялись.

Остаток: живая Telegram-приёмка на двух ПК — параллельные диалоги, allow/deny,
expiry, reconnect и независимая доставка ответа при отказе status edit.
Native Windows для этой итерации не проверялся.

Автоматические проверки перед финальным полным прогоном: Telegram commands/
controls/dashboard/delivery/usability/format/panel guards — **117 passed**,
42.400s (`dist/telegram-usability-verification/focused.xml`); two-connector
relay suite — **10 passed**, 12.270s (`multinode.xml` в том же каталоге).
Первый полный прогон нашёл устаревшее английское ожидание заголовка карточки
в multinode-тесте; оно обновлено к русскому интерфейсу, проверки allow/deny и
изоляции маршрутов сохранены.
Ruff check/format, diff whitespace и secret guard по изменённым файлам пройдены.

Финальное ревью обнаружило, что новый переход из задачи к диалогу должен быть
привязан не только к owned job и once-only callback, но и к текущим route/selection
revision: старая карточка не должна затирать более новый выбор из другого меню.
Граница добавлена в Panels; проверки подмены chat/message, повторного callback,
смены route и dialogue revision расширены на `/open_dialogue`.

Финальная проверка после усиления selection guards: **1358 passed / 35 skipped**,
216.717s; `dist/telegram-usability-verification/source-final.xml` и
`source-final.log`. Отдельные guards/usability — **24 passed**, 9.483s
(`selection-guards.xml`). Ruff check/format, whitespace и secret guard прошли.
