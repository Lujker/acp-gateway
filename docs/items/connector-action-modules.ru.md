# P4.16 — базовые действия ПК и подключаемые модули

**Статус:** DEFERRED — отдельный большой этап; runtime нет, scope уточнён 2026-10-20.
**Репозиторий:** `acp-gateway`.

## Решение владельца и границы

Уточнение 2026-10-20 заменило прежнее исключение встроенных функций: рядовые
действия, например выключение/перезагрузка ОС и перезапуск агента, предполагаются
в поставке. Точный набор, OS-права, владение процессом и подтверждения выбираются
перед реализацией; это не разрешение сейчас останавливать ПК или чужой Desktop.

Произвольные алгоритмы пользователь пишет и подключает как scripts/modules.
Пример Happ остаётся пользовательским расширением, не встроенной интеграцией.
Два слоя — базовые действия и модули — один отдельный большой этап, не часть
ближайшего [P4.17](connector-pairing.ru.md)/[P4.15.1](updates-out-of-box.ru.md).
Остальная архитектура ниже — прежнее предложение для модульной ветки, не готовый API.

Ниже — рекомендуемый контракт для обсуждения, ещё не утверждённый API.
P4.15 remote update остаётся отдельной задачей: универсальный исполнитель
не заменяет независимый updater, drain, health и recovery.

## Связь с задачами и расписанием P4.11

Решение владельца 2026-10-15: определения задач, расписания, scheduler и Run
находятся на коннекторе. Task имеет module executor или agent executor с prompt.
Ручной запуск и due идут через единый локальный Task Service; dispatcher и CLI
управляют теми же записями с revision checks. Работающий connector продолжает
разрешённые local policy задачи без dispatcher, сохраняя результаты/уведомления
для синхронизации после reconnect. Подробности — [P4.11](scenarios-and-schedules.ru.md).

Action Runtime этого документа — исполнитель module ветки. Local Task Run не
требует живого connection epoch: он авторизуется локальной task authority.
Привязка remote подтверждения к epoch относится к непосредственному remote
запуску; разрешение расписания имеет собственную revision/expiry policy.
Management API также предоставляет task CRUD, schedule pause/resume, run-now,
run history/status/cancel через общий Task Service, не второй scheduler.
AgentExecutor не реализуется обычным script runner: ему нужны local sessions,
agent policy, approvals и сохранение результата без участия relay диспетчера.

## Что уже есть в исходниках

- `connectors/protocol.py`: строгие bounded frames, Hello v1/v2 объявляет
  агентов; общий набор frames пока Open/Opened/Data/Close и heartbeat.
- `connectors/control.py`: аутентификация computer grant, проверка generation,
  замена подключения, выдача connection_id и отзыв доступа.
- `connectors/relay.py`: один reader/writer WebSocket, bounded ACP streams.
- `connectors/catalog.py`: каталог agent profiles из регистрации; для действий
  нужен отдельный каталог на уровне компьютера, не фиктивный AgentProfile.
- `connectors/maintenance.py`: локальный file-based maintenance контракт,
  резервирование и наблюдение активности. Это не удалённый API действий.

Следовательно, нужны новые versioned management frames и обработчики. Добавить
поля в старый Hello недостаточно: действующий decoder запрещает лишние поля и
неизвестные версии. Старый dispatcher/connector продолжает агентскую работу,
но не показывает неподдерживаемые действия. Согласование версии выполняется
до передачи новых frames; downgrade не должен случайно включать управление.

## Состав системы

1. Локальный module registry: явный allowlist в конфигурации коннектора,
   чтение manifest и проверка наличия runner. Каталоги автоматически не сканировать
   с исполнением найденного кода. По умолчанию список модулей пустой.
2. Connector Action Runtime: validation, local policy, reservation, durable journal,
   запуск отдельного процесса, bounded output, status и capability-gated cancel.
3. Action Catalog диспетчера: public metadata доступных действий конкретного
   computer_id, revision/digest каталога, online и enabled. Локальные пути,
   environment, секреты и команды запуска остаются на компьютере.
4. Общий application service: авторизация, подтверждение, operation intent,
   dispatch/status/cancel и аудит; Telegram/CLI/API используют один контракт.
5. Telegram renderer: компьютер → действия → параметры → подтверждение →
   карточка операции. Недоступные/устаревшие actions не запускаются.

Транспорт — существующее исходящее WSS-соединение. Коннектор не открывает
публичный HTTP-сервер. Один reader/writer остаётся владельцем сокета; management
сообщения получают отдельные bounded очереди и лимиты параллельности, чтобы
длинный вывод модуля не блокировал heartbeat, ACP и approvals.

## Авторство модуля и контракт процесса

Рекомендуется внешний executable/script с JSON input/output, без импорта
пользовательского Python в процесс коннектора. Это поддерживает Python,
PowerShell и любой язык без обязательного SDK. SDK/генератор шаблона можно
добавить позже как удобство; для первого прохода достаточно описания протокола
и тестового фиктивного модуля, не набора административных функций.

Пример локальной регистрации, **проектируемый формат**, не текущая конфигурация:

```yaml
modules:
  - id: local.backup
    manifest: /opt/my-actions/backup.manifest.json
    argv: [/usr/bin/python3, /opt/my-actions/backup.py]
    enabled: true
```

В public manifest: module id/version, protocol version, action id/title/description,
input/output schema, effect (read/mutate/disconnect), required confirmation,
max duration, concurrency group, execution affinity (idle/parallel/exclusive),
cancellation support. Для action descriptor формируется digest, включая
локальную revision реализации. Смена runner/manifest инвалидирует старые
подтверждения; hot reload и распространение модулей через диспетчер вне MVP.
Первый вариант — перечитать реестр при restart коннектора.

Для первого UI достаточно ограниченного профиля схемы: object с известными
string/number/boolean/enum полями, required, bounds, запрет дополнительных
полей. Без внешних `$ref`, исполняемых validators и HTML из manifest.
Telegram wizard имеет лимиты шагов/длины/TTL и отмену. Secret inputs в первом
MVP не вводятся через Telegram: модуль читает локально разрешённые секреты;
публичный выбор использует идентификатор заранее настроенного ресурса.

Input runner: operation_id, action_id, validated params, deadline и минимальный
execution context. Actor metadata не заменяет проверку прав в коннекторе.
Stdout — bounded JSON lines: progress и один terminal result; stderr — ограниченные
redacted diagnostics. Exit code/terminal result должны согласоваться; исчезновение
процесса без достоверного результата не означает успех. Схема результата,
лимиты записей/байтов и срок хранения задаются платформой, а не только модулем.
Точные поля и framing нужно закрепить protocol tests до реализации UX.

Запуск: фиксированный локальный argv, `shell=False`, параметры JSON через stdin,
фиксированный cwd, allowlist environment. Никакой подстановки параметров в shell
строку, произвольных команд/путей от диспетчера и автоматического elevation.
Права — права service account. Отдельный процесс изолирует сбой runtime, но
**не является sandbox**: подключаемый код доверенный и может делать всё, что
разрешено его OS-пользователю. Если нужна защита от недоверенных модулей,
необходимы отдельные OS accounts/контейнеры и отдельный scope проекта.

## Несколько действий и многошаговая логика внутри модуля

Один module manifest может объявить несколько actions; все направляются одному
runner с разным action_id. Task фиксирует одно такое действие и параметры.
Действие вправе выполнять собственную последовательность шагов/ветвлений и
выдавать progress. Это не требует общего workflow engine и агентского промпта.
Платформа проверяет каждый публичный action отдельно; внутренние шаги выполняются
в рамках предоставленных модулю OS прав, не получают отдельную policy магически.

Пример владельца: пользовательский модуль `local.happ`. Предлагаемые действия:

| Action | Смысл |
| --- | --- |
| status | Проверить процесс, состояние подключения и выбранный сервер |
| ensure_connected | При необходимости запустить приложение, выбрать сервер, подключить и проверить результат |
| disconnect | Явно отключить соединение, если пользователь добавит такую функцию |

У ensure_connected параметры могут выбирать server_ref/name или selection_policy
(например ordered_available/lowest_latency). Имена режимов — пример API будущего
модуля, не команды Happ. Режимы выбора лучше сделать взаимоисключающими.
При совпадающих именах серверов нужен устойчивый ID или отказ с уточнением;
никакого случайного выбора. Проверки latency сами по себе не доказывают успешную
работу туннеля: после connect нужен отдельный ограниченный connectivity probe.

Внутренние шаги ensure_connected: проверить текущий процесс и подключение →
если нужное подключение уже исправно, вернуть unchanged → при отсутствии
процесса запустить и дождаться готовности с timeout → выбрать сервер →
подключить → проверить фактический результат → вернуть connected/server/evidence.
Выбор по алгоритму выполняется локальным кодом без LLM. Повторная периодическая
проверка не должна без необходимости перезапускать приложение/туннель.

Status может быть read-only; connect/disconnect — mutating и разделяют общую
resource/concurrency group, в том числе между direct action и Task runs.
Failure не должен автоматически завершать чужой процесс или отключать исправное
предыдущее подключение. Границы retries отдельных проверок и побочных эффектов
задаёт автор модуля; unknown mutation не разрешает повтор всего сценария.
Изменение VPN может разорвать WSS: результат хранится локально, не объявляется
ошибкой только из-за outage dispatcher.

Конкретная интеграция Happ пока не исследована до рабочего контракта. Проверены
[официальные app-management docs](https://github.com/HappDev/happ_su/blob/main/dev-docs/app-management.md)
и [desktop repository](https://github.com/Happ-proxy/happ-desktop): наличие
subscription settings/deeplinks не доказывает API выбора сервера и connect для
установленной Windows-версии. До реализации проверить именно локальные API/CLI/
deep links, методы наблюдения состояния и режим запуска приложения. Если требуется
UI automation, отдельно проверить работу в пользовательской сессии и background
connector режиме; отсутствие подходящего управления означает unsupported,
а не фиктивный успех. Happ не становится встроенным модулем gateway.

## Права и подтверждения

Доступ = права actor на компьютер/action ∩ локально разрешённые действия ∩
поддерживаемые capabilities. Manifest не выдаёт разрешений. Local policy может
повысить уровень подтверждения, запретить action, ограничить параметры, время,
вывод и конкурентность; модуль не может её ослабить. Без явной policy включения
действие не доступно для удалённого запуска.

Подтверждение привязано к actor/channel, computer_id, grant generation,
connection epoch, action/module revision, нормализованным параметрам и сроку.
Перед dispatch и перед локальным start проверки повторяются. Reconnect до старта
инвалидирует старую кнопку; reconnect после старта допускает только query/reconcile
по существующей операции. Отзыв доступа не откатывает уже совершённые действия;
остановка работающего модуля определяется локальной cancel policy.

Для MVP существующий single-owner. Для shared выпуска требуется P4.10 actor/
workspace/connector scopes. ACP approvals и `/mode auto` не дают модели права
запускать management actions. Доступ AI-агента к этим функциям — отдельное
будущее решение, не часть пользовательского управления и локального scheduler.

## Протокол операций и неизвестные исходы

Логические методы: list capabilities, execute, get operation, cancel operation.
Названия wire frames определяются после version negotiation. Execute содержит
operation_id, computer identity, ожидаемые revisions/epoch, параметры, deadline
и авторизованный execution context. У пользователя — отдельный ActionOperation,
не prompt/Job в агентском диалоге; conversation/cwd агента не меняются.

Диспетчер сохраняет intent до отправки. Коннектор сохраняет operation ID,
request digest и состояние до запуска процесса. Повтор ID с тем же payload
возвращает существующую запись, с другим payload отклоняется. При падении между
journal и запуском/побочным эффектом возможен unknown: это не exactly-once.
Удалённые идентификаторы хранятся/помечаются достаточно долго для дедупликации;
очистка journal требует retention policy, а не разрешения повторить старый ID.

Состояния: pending_confirmation → dispatching → accepted → running →
succeeded/failed/cancelled; отдельно rejected, expired-before-start и unknown.
Deadline запрещает поздний start, но не доказывает остановку уже начатой работы.
Timeout/разрыв WSS/нет ACK переводят наблюдение в unknown, автоматического replay
мутаций нет. Query после reconnect не выполняет действие повторно. Offline
компьютер не принимает remote run: отказ без скрытой очереди. Работающие
локальные расписания независимы от соединения с dispatcher (P4.11).

Cancel — запрос только при объявленной поддержке, с отдельным результатом;
убийство процесса не обещает отмену внешнего эффекта. Для действий, выключающих
свой connector/ПК, accepted значит только принятие. Итог может остаться unknown;
проверка после reconnect возможна только с доказательством от journal/модуля.
Для надёжного update/restart требуется внешний supervisor, а не длинный handler
внутри отключаемого connector.

## Предлагаемый порядок реализации

1. Зафиксировать manifest, version negotiation, policy и lifecycle; тестовый
   модуль без системных эффектов. Проверить совместимость старых peers.
2. Локальный opt-in registry/runner с валидацией, лимитами, journal и дедупликацией.
3. Versioned management transport + каталог/action service/аудит на диспетчере.
4. Telegram generic формы/подтверждения/карточки; status/reconcile/cancel.
5. Изолированная Linux/Windows приёмка; пользователь подключает свой модуль.

Критерии: пустой registry не объявляет действий; невалидный module не исполняется;
чужие/старые approvals отклоняются; params валидируются с обеих сторон;
duplicate click не создаёт вторую операцию; crash/ACK loss/reconnect не повторяют
мутацию; busy/exclusive согласованы с агентской активностью; объём stdout ограничен;
вывод не блокирует ACP/heartbeat; Linux/Windows process cleanup проверен.

## Решения для следующего обсуждения

- Подтвердить внешний JSON runner как основной формат вместо Python-only plugin API.
- Сначала локальная установка и restart registry, без remote install/hot reload.
- Выбрать первый пользовательский модуль для проверки контракта; он не становится
  встроенной функцией поставки. До этого реализацию не начинать.
