## Проблема и подтверждённый путь

Ближайший этап решает затруднения нынешнего владельца при подключении и обслуживании
своих ПК. Это не запуск сервиса для независимых пользователей.

1. На целевом ПК запустить CLI коннектора; ввести IP:port/DNS диспетчера и ID владельца.
2. Коннектор создаёт запрос и показывает данные для сверки конкретного запроса.
3. В уже авторизованном профиле владельца подтвердить запрос через Telegram или
   CLI диспетчера. Простая кнопка без возможности сверки своего запроса недостаточна.
4. Приложение само создаёт и сохраняет отдельные данные доступа устройства.
5. Мастер помогает выбрать/проверить агента и предлагает автозапуск коннектора,
   не устанавливая и не перенастраивая агента молча.
6. Успех — готовый маршрут в Telegram, через который можно явно создать диалог
   и отправить задачу. Регистрация без ready-agent — промежуточное состояние.

Пароль, перенос файлов ключей, редактирование YAML и перенос fingerprint не входят
в обычный путь. При отсутствии агента, авторизации или запущенного backend мастер
объясняет следующий шаг, а не выдаёт фиктивный ready и не извлекает секреты скрытно.

## Владелец и транспорт

ID владельца стабилен, показывается в профиле и не является секретом или authority.
Сейчас один профиль: без регистрации посторонних, паролей, восстановления аккаунтов,
sharing и биллинга. Сервер проверяет принадлежность устройства; заявитель не может
назначить себе чужого owner. Telegram/CLI вызывают один application service.
Будущие VK и P4.10 используют ту же модель; Telegram ID не становится универсальным
user ID. Минимальная owner identity не считается готовой multi-user изоляцией.

WSS рекомендуется. WS разрешён для самостоятельного развёртывания, не только тестов:
явное предупреждение об отсутствии шифрования и согласие; автоматический downgrade
WSS → WS запрещён. Подтверждение привязки не делает WS защищённым. Простой проверяемый
WSS bootstrap для IP/DNS и proxy paths требует отдельной технической проверки.

## Однократная миграция старых ПК

Владелец сначала согласился сохранить привязки, затем явно изменил решение:
при переходе все прежние ПК проходят новый путь. Это один переход, не rebind после
каждого будущего update. После него обычные обновления сохраняют новую привязку.

- При включении нового механизма legacy credentials не дают рабочего доступа;
  коннектор показывает migration-required и предлагает мастер вместо бесконечного retry.
- Сохраняются настройки агентов, названия, история, результаты и записи компьютеров.
  Перепривязка — не reset, удаление БД или новая настройка агента.
- Связь с прежней записью подтверждает владелец. Совпавшие alias/hostname/computer ID
  сами по себе не разрешают замену устройства.
- Новая привязка отзывает прежнюю authority, включая старые соединения/credentials;
  hidden legacy fallback запрещён.
- История/результаты отделены от attachment: продолжение живого Hermes-диалога
  после рестарта не обещается.
- До выпуска доказать upgrade order, переход ещё не перепривязанного ПК и rollback
  boundary: требование rebind не должно блокировать сам upgrade.

## Приёмка

1. Новый ПК: весь путь до ready-agent/new dialogue без ключевых файлов/YAML.
2. Telegram/CLI: одна операция; deny/expiry/repeat не выдают доступ; чужой actor,
   подменённый target и неверные данные сверки отклоняются.
3. Повтор мастера, lost ACK/reconnect не создают дубликат или самовольную замену ПК.
4. Старый ПК: обязательный однократный rebind без потери данных; legacy credential
   отозван; следующее обычное обновление не требует нового rebind.
5. WSS errors/no downgrade, явное WS consent, нет секретов в логах; offline/denied/
   agent-not-ready/service-not-ready показывают понятное следующее действие.

Автотесты готовит агент; ручной smoke на своих установках делает владелец. Не нужны
другие тестировщики, календарный deadline или повтор всей ранее закрытой приёмки.

## Вне этапа и технический остаток

Вне scope: multi-user, VK runtime, Goose parity, OS/process actions, modules/Happ,
расписания, mobile, импорт локальных диалогов и shared write. Обновление обеих ролей
без ручного companion обслуживает связанный P4.15.1.

Перед кодом проверить applicant binding/выдачу credential и recovery, bootstrap
единственного владельца, bounded pre-auth ingress, WSS и migration/rollback.
Точные команды, API, limits и migrations пока не утверждены.

## Журнал — 2026-10-20

Реализация P4.17 выполнена в рабочей ветке `feat/connector-pairing-managed-updates`:
owner bootstrap, ограниченный pre-auth ingress, durable request/approve/deny/claim/

маркер `data_dir/pairing-boundary.json`, CLI/Telegram approval, мастер `acpgw connect`,
обновление аргументов managed service и однократная активация legacy rebind.

Найдены и исправлены три дефекта recovery-путей: периодическая очистка удаляла
просроченную запись `issued` до потерянного ACK; просроченный `issued` нельзя было
получить повторно; `denied` нельзя было локально отменить, из-за чего мастер
застревал на старой заявке. Теперь очистка удаляет только незавершённые терминальные
заявки, уже выданный credential остаётся восстановимым до ACK, а `denied` можно
локально закрыть. Мастер при неотправленном ACK не предлагает заменить такую
заявку новой, пока активация не завершена. После активации границы `computers rotate`
обновляет generation привязки вместе с компьютером, а legacy `enroll` без привязки
отказывает с указанием пройти pairing вместо выдачи мёртвого credential. Контракт
updater: не удалять и не откатывать внешний boundary marker при восстановлении базы.

Проверено в WSL: полный набор **1734 passed, 38 skipped**; pairing-focused
**42 passed**; отдельные recovery-тесты потерянного ACK после expiry, cleanup и
`denied` cancellation — **3 passed**; Ruff check/format чистые. Живые сервисы,
GitHub/провайдеры и production не затрагивались.
