# P4.8: граница управления общим диалогом Hermes

Дата: 2026-10-12. Проверена установленная версия Hermes Desktop 0.21.6.
Production-перевод в ACP/relay ещё не включён. Это решение о текущей границе
доступа и требования для следующего этапа, не описание готовых upstream API.

## Что подтверждено

Два клиента могут подключиться к одному живому backend и диалогу. Нативный
Windows тест подтвердил поток ответа и сохранённую идентичность. Повторный
тест без модели подтвердил подключение diagnostic creator + observer peer.

Отдельный compatibility lab исполнил реальный код установленного Hermes
на синтетическом состоянии в памяти, без сервера, модели и выполнения команд:

| Проверка | Наблюдение |
|---|---|
| Busy submit | `queue` → queued; `steer` → steered; `interrupt` → redirected при поддержке redirect |
| Старый агент без redirect | Режим interrupt ставит запрос в очередь и прерывает текущий ход |
| `queued=true` | Принудительная очередь; это не отказ и не запрет будущего выполнения |
| Поздний `session.interrupt` | Прерывает текущий ход сессии, включая последующий ход Desktop |
| `expected_hosted_task_id` | Защищает hosted-room task, не обычный чат; отказ всё равно вызывает stop глобального TTS |
| Ответ на approval | Первый ответ выигрывает; повторный/поздний ответ отвергается |
| Отмена/таймаут запроса | Ожидание завершается без разрешения, ответ после завершения не принимается |

Артефакты: [fixture](../../tests/fixtures/hermes/0.21.6/README.md),
`scripts/spike_hermes_semantics.py`, opt-in `test_hermes_semantics.py`.
Это проверка обработчиков upstream с подменёнными agent/persistence hooks,
а не живая приёмка исполняемого инструмента и GUI.

В исходнике также обнаружен auto-continue при cold `session.resume`: Hermes
может продолжить незавершённый ход без нового prompt клиента. Параметр
`omit_messages` этого не отменяет. Произвольный resume нельзя использовать
как безопасную read-only диагностику или автоматический reconnect Gateway.

## Реализованная граница

- Обычный `HermesRpcClient` работает как observer. Он блокирует create, resume,
  prompt и interrupt; live activation требует `omit_messages=true`.
- Observer не объявляет способность отвечать на server requests и не отвечает
  на полученные общие вопросы. Автоматический deny или `-32601` мог бы завершить
  чужой approval раньше пользователя Desktop.
- Только explicit diagnostic mode разрешает тестовые изменения. Prompt/interrupt
  и автоматические ответы привязаны к одному явно выбранному live ID/профилю;
  смена привязки и дополнительные поля mutation, включая truncate, запрещены.
  Это лабораторный доступ, а не доказательство эксклюзивного владения у upstream.
- Второй клиент spike всегда observer. Cold resume требует отдельного
  `--allow-auto-continue`; неудачный activate не подменяется resume.
- Probe публикует режим доступа отдельно от готовности API. `ready` не означает
  готовность безопасного управления общим диалогом.

## Что нужно для production shared control

Требуется upstream-гарантия либо другой интерфейс с эквивалентной семантикой:

1. **Атомарный приём хода и владение.** Проверка idle и выдача непрозрачного
   turn ID должны происходить в одной операции с постановкой running. Пока
   действует владение ходом, другие пути submit/steer/redirect не должны
   скрытно менять его. Явный пользовательский takeover должен отзывать владение
   и уведомлять коннектор. Проверка busy на клиенте или mutex Gateway этого
   не обеспечивают: Desktop обходит такой mutex.
2. **Отмена конкретного хода.** Отмена должна ссылаться на выданный upstream
   turn ID/generation и воздействовать на его cancellation handle. Одной
   проверки ID до асинхронного interrupt недостаточно: между проверкой и
   фактической отменой может начаться новый ход. Отказ по старому ID не должен
   останавливать TTS или инструменты нового хода.
3. **Привязка событий и вопросов.** Stream, completion и approvals должны
   однозначно относиться к выбранным backend/profile/session/turn/epoch.
   Для нескольких approvers нужен авторитетный результат settlement, чтобы
   проигравший ответ не показывался как применённый, а карточки удалялись.
   На первом этапе не передавать persistent `session/always` grants.
4. **Восстановление без исполнения.** Повторное подключение/чтение сохранённого
   диалога должно явно запрещать auto-continue. При неизвестном исходе prompt
   не повторяется; прежняя turn authority не переносится на новый backend.

Названия возможных полей вроде `if_idle`, `expected_turn_id` или capability
`guarded_shared_turns` — предложения для согласования с upstream, сейчас их
поддержка не заявляется. Исходники и конфигурация установленного Hermes не менялись.

Пока такой гарантии нет, общий пользовательский диалог доступен для observation,
а shared write/cancel остаётся закрыт.

## Выбранный MVP: отдельные диалоги диспетчера

2026-10-12 владелец явно выбрал: «Отдельные диалоги диспетчера в том же
запущенном Hermes; отдельно проверить ограничения владения».

`adapters/hermes.py` реализует первый слой этого режима без запуска второго
Hermes. Диалоги создаются самим драйвером; произвольный live/stored ID нельзя
выдать за принадлежащий диспетчеру. Привязка ограничена текущим соединением,
профилем и backend identity. При обрыве handles становятся недействительными;
при timeout prompt или не streaming-ответе диалог получает состояние uncertain,
повторная отправка запрещается. Обнаруженный посторонний ход тоже отнимает
право записи. События чужих диалогов отбрасываются.

Это локальная политика, а не блокировка в Hermes. Пользователь должен оставлять
эти диалоги для диспетчера: чтение в Desktop допустимо, параллельные prompt,
steer, redirect и отмена из Desktop нарушают предположение о единственном писателе.
Клиент не способен обнаружить все гонки внутри уже идущего хода.

Cold resume, импорт диалогов и interrupt в драйвере отсутствуют. Обычный driver
по умолчанию отклоняет собственные запросы. ACP bridge явно включает передачу
запросов человеку: только once/deny, без session/always. Чужие вопросы остаются
без ответа. Отзыв upstream-вопроса отменяет ожидающее human approval в ядре,
поздние ответы не отправляются агенту. Передача проверена через реальный WS
relay против mock backend, без модели или инструментов.

Отправка решения не является подтверждением победы в first-response-wins:
`approvalSettlementConfirmed=false`. Решение человека и исполнение действия
различаются; из Desktop не следует параллельно отвечать на approvals этих диалогов.
Bridge передаёт только запросы, которые Hermes сам решил запросить. Он не вводит
дополнительный approval для каждого инструмента и не меняет профильную политику
Hermes. Настройки auto/YOLO и grants в самом агенте требуют отдельной проверки
перед живой приёмкой; ACP cwd policy не является файловой песочницей.

Транспорт доступен через локальный `backend: hermes` и существующий connector.
Ядро явно отклоняет cancel до изменения job/approval state. Настройка пока ручная;
сохранение привязок, безопасное recovery и Windows/VPS/Telegram приёмка открыты.
