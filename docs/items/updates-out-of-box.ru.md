# P4.15.1 — обновления из коробки через CLI и Telegram

> Решение владельца от **2026-10-27**: оставшаяся приёмка выпущенных функций
> предварительно закрыта (**PROVISIONALLY CLOSED**), из активной очереди снята.
> Возвращаться только по конкретным проблемам. Это решение не добавляет новых
> результатов проверок и не закрывает ещё не реализованные функции.
> Диспетчер и home — 0.2.8 по журналу выпуска; work обновлён до 0.2.8
> успешно по сообщению владельца, способ обновления не уточнён.

**Статус:** PARTIAL — updater и ACL/preflight выпущены; их остаточная приёмка
PROVISIONALLY CLOSED владельцем 2026-10-27. Docker companion UX и Git updates
остаются разработкой P4.19. Успешное обновление work до 0.2.8 сообщено владельцем,
способ обновления не уточнён и не является доказательством Telegram round trip.
**Решение владельца:** 2026-10-16; scope/порядок подтверждены 2026-10-20 после grill-me.
**Приоритет при возобновлении:** базовая эксплуатационная возможность.

Проверка последней версии и обновление диспетчера/коннекторов должны поставляться
из коробки и быть включены по умолчанию. Пользователю достаточно обычной установки
и настройки приложения; отдельная настройка updater делает базовую функцию слишком
сложной. Задача продолжает [P4.15](remote-connector-management.ru.md).

## Требуемое поведение

- Из CLI можно проверить последнюю доступную stable-версию и обновиться простой
  командой. Существующие `acpgw update --check`, `acpgw update --stable` и выбор
  точной версии должны предоставлять единый понятный путь. Нужную роль, способ
  установки и lifecycle службы приложение определяет автоматически.
- Через диспетчер и его каналы (сейчас Telegram) доступны проверка версии и обновление диспетчера или выбранного
  коннектора. Возможность включена по умолчанию и доступна штатному владельцу;
  отдельного opt-in `updates.enabled: true` не требуется.
- Установка новой версии запускается явной CLI-командой или подтверждением
  конкретной цели/версии в Telegram. Автономная установка по таймеру не запрошена.
- Независимый worker может оставаться внутренним механизмом. Обычная установка
  или первый запуск автоматически подготавливает его, устанавливает автозапуск
  и проверяет готовность. Обновление приложения обслуживает и обновляет worker.
  Пользователь не управляет отдельной службой ради обычного обновления.
- Config/env, spool, executable и service paths определяются из действующей
  установки. Ручные JSON policy и команды `updater install/enable` не требуются
  для стандартного сценария; advanced-настройки могут оставаться дополнительными.
- Для uv поддерживаются диспетчер и коннекторы в рамках доступных платформенных
  service adapters. Сохраняются данные, ключи, конфигурация и состояние службы.
- Для Docker host-компонент поставляется как часть штатного развёртывания.
  Проверенный образ нужной версии автоматически находится, скачивается и
  закрепляется по immutable digest; ручной `allow-image` для каждого релиза
  не требуется. Host-компонент продолжает работать при пересоздании gateway.
- CLI и Telegram показывают одинаковую доступность версии с учётом реально
  опубликованных артефактов для выбранного backend, состояние операции и итог.
  Сохраняются idle/drain, backup, health/recovery и отсутствие replay при unknown.
- Занятые targets не обновляются и не получают скрытое отложенное задание: показывается
  причина, после завершения работы нужна новая явная команда. Предупреждение о возможной
  потере продолжения диалога показывается до подтверждения. Сохранённые результаты
  обязательны; cold resume после restart не входит в этот этап.
- Механизм P4.15 переиспользуется, не переписывается заново в Telegram handler.
  Будущие каналы вызывают общий service; local CLI остаётся доступным.

## Критерии готовности

1. После стандартной установки/первого запуска проверка версии и обновление
   доступны через CLI и Telegram без отдельного шага включения updater.
2. После reboot, обновления приложения и перезапуска контейнера механизм остаётся
   готовым; его внутренние компоненты не требуют ручной переустановки.
3. Новый stable-релиз устанавливается через каждый интерфейс на uv и Docker
   без ручной подготовки policy или списка разрешённых образов.
4. Пользователю видны конкретные target/version, ход и сохранённый результат;
   ошибка или потеря соединения не приводят к повторной установке вслепую.

## Текущее состояние и очередь

В **0.2.1** выполнение обновлений по-прежнему выключено по умолчанию, companion
настраивается отдельно, а Docker требует заранее подготовленного разрешённого
образа. Этот документ задаёт следующий целевой UX и не объявляет его реализованным.

## Актуальное решение — 2026-10-20

Владелец подтвердил этап для себя: сначала [P4.17](connector-pairing.ru.md), затем
упрощение уже существующего remote update обеих ролей. Полноценный multi-user,
VK/Goose и OS actions/modules не включаются скрыто. Для нового pairing предусмотрен
однократный rebind старых ПК; обычные следующие updates сохраняют привязку.

Разрешены фиксация требований и подготовка плана; код, релиз и изменение рабочих
defaults/установок не разрешены. Историческое DEFERRED от 2026-10-16 заменено этим
порядком, не утверждением о готовности. Приёмка ранее закрытых треков не возобновляется.
Дополнительно проверить busy refusal/new command, сохранность результатов и последующий
update без повторной привязки. Автотесты — агент, ручной smoke — нынешний владелец.

## Последующее поручение — 2026-10-20

Владелец поручил разработку P4.17 и P4.15.1. Прежнее ограничение только
документами заменено разрешением реализации и локальных тестов. Публикация,

## Журнал — 2026-10-20

Реализованы `update_bootstrap` (выбранная роль, private policy, независимый runtime
и autostart, честная проверка heartbeat), безопасное обновление helper с digest и
lease, автоматическая подготовка Docker host companion, официальный immutable GHCR
delivery без per-version `allow-image`, общий artifact gate CLI/Telegram и durable
busy/unknown guards. `UpdateSettings.enabled` теперь `true` по умолчанию; явный
`false` остаётся opt-out. Обычный `acpgw update --check/--stable/--version` использует
общие проверки артефактов, автоматически выбирает managed role/coordinator, а Docker
отправляет операцию через локальный spool без Docker socket в контейнере.

Интеграция выполнена в daemon/connector startup: provision запускается фоновой
задачей после того, как health/control может отвечать, а не блокирует запуск.
Read-only команды bootstrap не вызывают. В wizard после установки основной службы
updater готовится и сообщает `ready` либо причину отказа. `stage-runtime` обслуживает
self-refresh worker без загрузки конфигурации и служб.

Проверено в WSL: полный набор **1734 passed, 38 skipped**; Ruff check/format чистые.
Реальные read-only проверки PyPI/GHCR metadata выполнялись при разработке, но
живой installer/service/container и Telegram не запускались.

Остаётся до READY: native Linux/Windows upgrade с Task Scheduler/systemd re-exec,
реальный Docker replacement/rollback и health, Telegram round trip, reboot/logon
persistence и owner smoke. Git/file/binary/macOS/Windows dispatcher не входят в
автоматический путь; неподдерживаемый режим должен сообщать отказ, не fake ready.

## Журнал — 2026-10-26

Первая живая попытка обновить коннектор из Telegram: work-ПК владельца (Windows,
uv registry 0.2.2, Hermes) → stable 0.2.3, сразу после публикации 0.2.3.

- **Check versions** в 10:39 UTC вернул latest 0.2.2: JSON PyPI ещё отдавал кэш
  через несколько минут после публикации. Повторная проверка позже увидела 0.2.3.
- Обе операции (`9e2a298c…`, `b1afc93a…`) завершились `failed/failed` через 10 с:
  `update --status` на ПК — `phase: preflight`, `ValueError`, служба не
  останавливалась. `maintenance --role connector status` без перезапуска
  переключался между `unknown` и `running`.
- **Причина:** в 0.2.2 watcher публикует `connector-activity.json` каждые 0,2 с через
  `_atomic`, а на Windows это три дочерних ACL-проверки на запись. На рабочем ПК
  (корпоративный антивирус проверяет каждый запуск `pythonw.exe`) цикл иногда
  дольше 5 с — порога свежести `read_status`, и preflight видит `unknown`. Кроме
  того, в 0.2.2 `ValueError` проверки (таймаут) молча завершает watcher: перехвачен
  только `OSError`. Тот же механизм на ПК владельца постоянно показывал курсор
  «фоновая загрузка».
- **Обход:** остановить задачу коннектора → `update --version 0.2.3 --with-services`
  (для остановленной службы проверка активности пропускается) → `succeeded`.
  Updater вернул задачу в исходное состояние «остановлена», поэтому её пришлось
  запустить вручную; коннектор переподключился в 10:59 UTC. Это ожидаемое поведение
  restore, не дефект, но в обходе его нужно называть явно.
- **Исправлено в 0.2.3** (`65c9dfc`, `edbb1a3`): обычная запись статуса без ACL-проверок,
  полная проверка каталога при старте и раз в 60 с, `ValueError` проверки повторяется.
- **Последующее исправление:** `99cc9ba` переносит периодическую ACL-проверку
  в фоновую запись отдельного marker; `e732a4b` считает срок от начала проверки.
  При ошибке или истечении 60 с запись heartbeat блокируется. Это входит в 0.2.6;
  прежний пункт «вынести ACL из пути публикации» выполнен.
- **Остаток:** успешный Telegram round trip после исправления. Ручной перевод
  диспетчера на GHCR 0.2.7 с backup и проверками выполнен, но не доказывает
  обновление через host companion. См. [0.2.7 publication](../releases/0.2.7-publication.md).
- `64425d6` исправляет зависание/флаки тестов maintenance; релизный CI 0.2.7
  прошёл. Это тестовое исправление, runtime коннектора в 0.2.7 не менялся.
