## Проверенная исходная база

- `cli/computers.py`/`storage/computers.py`: export credential, digest, enabled,
  generation, rotate/revoke и уведомление подписчиков.
- `cli/wizard.py:_connection`, `setup_state.py`, `connectors/launch.py`: требуют
  server URL/computer ID/token file и сохраняют connection/service arguments.
- `connectors/control.py`/`relay.py`: authentication, generation/epoch fencing;
  новый pairing не должен обходить эти границы.
- `config.py:TelegramSettings`: allowlist, не accounts. Owner HTTP API остаётся
  локальным административным: не публиковать его наружу ради enrollment.
- P4.15 уже разделяет dispatcher control, durable local operation и независимый
  executor; pairing не заменяет updater и не требует module runner.

## Предлагаемые компоненты и данные

```text
CLI ПК → bounded pre-auth pairing ingress → PairingService → device registry/audit
                                                ↑
                     Telegram / локальный CLI → authenticated owner
                                                ↓
              credential только исходному заявителю → обычный connector auth/relay
```

Общий PairingService, тонкие adapters, отдельный ограниченный ingress без доступа
к jobs/агентам/owner API. Нужны payload/rate/expiry limits и отсутствие account
перечисления по разным публичным ответам; точные значения выбрать тестами.

Предлагаемые записи:
- OwnerProfile: стабильный internal ID и доверенные identities; один профиль.
  Если в прежнем allowlist несколько Telegram IDs, локально явно выбрать approvers,
  не объявлять всех владельцами автоматически.
- PairingRequest: random ID, owner, данные сверки, expiry, applicant binding,
  device metadata, new/rebind, optional previous device + revision, state/audit.
- DeviceBinding: стабильная запись ПК, owner, credential generation и migration
  boundary. Alias/hostname не предоставляют authority.
- Локальный pending/credential state: private paths вне заменяемого package env,
  без секретов в argv/logs/Telegram; сохраняется при update/restart.

## Lifecycle и безопасность выдачи

Логическая модель: pending → approved → claimed; rejected/expired/cancelled отдельно.
1. CLI создаёт private applicant state и запрос без постоянного доступа к серверу.
2. CLI и approver показывают одинаковые данные сверки/target. Rebind явно называет
   старую запись и предупреждает об отзыве прежней authority.
3. Approve проверяет actor, expiry, request digest/revision и target; решение
   транзакционно одноразовое, duplicate click возвращает существующий результат.
4. Claim доступен только исходному заявителю. Owner ID/request ID/данные сверки
   публичны и сами по себе не разрешают получить credential.
5. Define crash-consistent credential save/ACK/activation: потеря ответа не создаёт
   второе устройство или лишнюю generation; только потом обычный authenticated relay.

**Блокирующий технический вопрос:** выбрать и проверить applicant binding,
выдачу/повторное получение результата и activation recovery. Перед кодом проверить
подходящие стандарты/библиотеки по актуальным первичным источникам, не писать
самодельный криптопротокол по этому наброску. Флаг approved не заменяет защиту claim.
WS остаётся принятым незащищённым transport: pairing не скрывает этот риск и
не заменяет TLS собственным шифрованием. WSS не понижать до WS автоматически.

## Мастер и эксплуатация

Сохранять найденные config/env/data paths и agent profiles. Проверять отдельно
pairing, agent readiness и service/autostart. Изменённые connection arguments
обслуживать штатным service coordinator, не оставляя ручной reinstall пользователю;
любое прерывание/изменение службы показать заранее.
Повторный мастер: продолжить pending/status, явно отменить либо сменить connection;
без второй службы, duplicate device и скрытой смены active dialogue.

IP/DNS, root/subpath и reverse proxy требуют bounded endpoint discovery с проверкой
origin; секреты не уходят по redirect на другой сервер. WSS bootstrap без обычного
ручного fingerprint ещё проверить; сертификаты на любом IP автоматически не обещаны.
WS — только с явным предупреждением/согласием. Если Telegram недоступен, остаётся
авторизованный локальный CLI; offline/error не разрешают credential fallback.

## Миграция и rollback — проверить до выпуска

1. Backup согласованных данных, инвентаризация IDs/путей/служб и отдельная граница
   включения нового enrollment; не менять работающий production этим планом.
2. Подготовить dispatcher с local owner access и pairing ingress. При включении
   migration-required legacy credential больше не даёт relay/update authority.
3. Обеспечить локальное штатное обновление старого коннектора: миграция не должна
   зависеть от уже отозванного remote credential. Иной двухфазный rollout допустим
   только после доказательства, без hidden legacy bypass.
4. Запрос с каждого ПК; владелец явно выбирает прежнюю запись; стабильные IDs,
   историю/результаты сохранить, authority заменить атомарно.
5. Проверить старые credentials/connections/callbacks: доступа нет. Следующий
   обычный update не требует rebind; offline ПК проходит переход позднее явно.
6. Проверить crash/mixed-version recovery. Старый DB snapshot не должен незаметно
   воскресить legacy authority: boundary/rollback policy — отдельное обязательное
   техническое решение. При невозможности безопасного rollback — явный отказ.

## Подэтапы и evidence gates

| Подэтап | Проверяемый результат |
| --- | --- |
| Контракт | Закрыты claim/recovery, owner bootstrap, transport, migration/rollback; согласованы schema/API и negative tests |
| Registry/service | Транзакции, owner/target checks, deny/expiry/repeat, audit, bounded pre-auth ingress |
| CLI/Telegram | Один service; сверка запроса; duplicate callbacks/restart/lost ACK не создают доступ повторно |
| Ready-agent/service | Сохранены paths/profiles; mock pairing → route → new dialogue/result; нет скрытых installs |
| Миграция | Копия прежних данных, два ПК, обязательный rebind, legacy rejection, история, следующий update без rebind |
| Владелец | Ручной smoke на своих установках, не повтор всей прежней приёмки |

Crash points: approve/claim/save/ACK; чужой owner/target, collision alias, revoke race,
disk error, wrong server, WSS validation, WS consent, agent/service unavailable.
Pending/unknown не маскировать успехом; чтение status не повторяет мутацию.

Следом P4.15.1: текущий updater + автоматические companion lifecycle/paths/policy
и immutable Docker image delivery. Busy target отклоняется с причиной; после
освобождения новая команда, без скрытой очереди. Сохранять результаты и предупреждать
о потере attachment; unknown не replay. Подробный update plan дополняется после
сверки installation backend, не обещает parity непроверенных ОС.

## Альтернативы и открытые вопросы

Export key отвергнут как основной UX; bot-first перенос code заменён connector-first
запросом; пароль не нужен. Полный multi-user отложен; минимальная identity не равна
изоляции. Автозамена по alias запрещена. Script runner не заменяет updater.

Открыты технически: exact claim protocol и limits, bootstrap approver identities,
IP/DNS WSS discovery, безопасный rollout/rollback и поведение прерванного claim.
Эти вопросы закрывает исследование перед кодом, не дополнительное предположение
о согласии владельца. Вне scope: VK, Goose parity, OS actions/modules, расписания,
импорт локальных чатов, public user API/mobile. Реализация/публикация не разрешены.
