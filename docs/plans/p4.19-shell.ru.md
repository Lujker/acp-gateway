# P4.19.2 — прямые shell-команды: точка начала реализации

## Согласовано владельцем

`!команда` выполняется напрямую на ПК выбранного диалога в его cwd только
при локальном профиле `work`. `safe` отказывает. Название оболочки, ПК/cwd,
код завершения, таймаут и отмена видны в карточке. Карточка обновляется,
вывод автоматически не попадает в модель; отдельное «Передать агенту».
Формы ввода имеют приоритет над `!`. Topics не нужны.

## Исследованные точки подключения

- `connectors/protocol.py`: строгие `_Model`/`_Frame`, discriminated union
  `ControlFrame`, `Welcome` с согласуемыми расширениями.
- `connectors/control.py`: `connect_control` согласует расширения через
  handshake; `ControlDispatcher.profiles` проверяет регистрацию до и после
  RPC. `run_connector`/`_run_connection` передают handlers в `RelayPeer`.
- `connectors/relay.py`: один control reader/writer; `_update_rpc` связывает
  request/epoch/ожидаемый тип ответа, лимит 4; операции профилей занимают
  `update_workers`. Shell должен иметь собственную очередь/квоту, не занимать
  updater/profile workers на время длинной команды и не запускаться через
  resumable ACP `Data` (его replay мог бы повторить выполнение).
- `connectors/commands.py`: локальные `clients`, `policies`, `managers`,
  `ConnectorMaintenance`, `local_factory`. Здесь создаётся локальная служба shell,
  подключаются её status/cleanup и handler. Авторитет — текущая локальная
  конфигурация профиля, не присланное диспетчером поле mode.
- `adapters/wsl.py`: `spawn_wsl`/`close_wsl`, Linux supervisor и receipt
  очистки группы. Нельзя трактовать остановку Windows launcher как доказательство
  завершения Linux-потомков. Native Windows требует проверенной очистки дерева
  собственных процессов; не использовать общий `taskkill /IM` или остановку WSL.

## Порядок кода

1. Локальный журнал операций в приватном data_dir (`shell-operations.db`, отдельно
   от gateway.db): UUID операции, actor/alias/session/cwd, маскированная команда,
   состояния до запуска/выполнения/готово/неизвестно, результат. Резервировать UUID
   транзакцией **до spawn**; повтор UUID не исполняет команду заново. После restart
   незавершённые записи становятся unknown, автоматического replay нет.
2. Локальный исполнитель: проверка существующего профиля Codex/Claude work,
   локального cwd и принадлежности сессии. Goose/Hermes automatic execution
   не приравнивать к work. Фиксированная показанная оболочка в ОС профиля;
   gateway/relay/Telegram токены не наследуются окружением. Стандартный ввод
   интерактивных команд не поддерживается. Ограничить длительность, параллелизм,
   суммарный stdout/stderr и хранение результатов; cleanup при отмене/shutdown.
3. Согласуемый control extension с start/status/cancel, operation UUID и request
   UUID/epoch. Статус неизвестного исхода не запускает команду. Несогласованное
   расширение/старый connector выдаёт понятный отказ до исполнения.
4. Диспетчер сохраняет операцию и её точный маршрут до network await, проверяет
   владение при status/cancel/передаче результата; смена выбранного диалога
   не переносит операцию в другой диалог. Карточка результата содержит источник.
5. Telegram: распознавание после проверок форм, snapshot выбранного диалога,
   карточка в одном сообщении; отдельный контрол передачи вывода в исходный
   диалог агента, once-only + проверка выбора. Не передавать вывод в новый
   выбранный диалог по ошибке. История операции не считается историей модельного хода.

## Вывод и маскирование

Для первого варианта достаточно обновлять длительность/состояние, показывая
вывод после завершения: это исключает публикацию частично полученного секрета.
Собирать stdout/stderr с жёстким общим пределом, постоянно дренируя трубы.
Если предел превышен, можно отказаться от сохранения всего вывода и показать
понятную отметку; не публиковать сырой обрезанный префикс секрета. Если сохраняется
ограниченный фрагмент — маскировать **до** обрезки с тестом границы секрета.

## Реализованная локальная часть

`shell_journal.py`: отдельный private SQLite WAL/FULL, reserved/running/terminal/
unknown/expired, атомарный UUID, привязка к actor/alias/session/cwd/command/timeout,
маскированные command/output. После crash reserved/running становятся unknown
только при восстановлении exclusive executor. Полные записи ограничены 1024,
идентификаторы — 100000; expiry очищает содержимое, оставляя tombstone против replay.
Дубликат UUID проверяется до лимита и возвращает старое состояние без исполнения.

`shell_runner.py` + `_shell_worker.py`: Linux sh и подготовленная WSL bash ветка
через существующий verified supervisor. Worker не создаёт вложенную process
group: вся команда и обычные потомки остаются в группе supervisor. STDIN DEVNULL;
stdout/stderr собираются ограниченно и дренируются, после 60000 байт вывод
отбрасывается целиком. После завершения shell worker недолго ждёт EOF pipes;
зависший pipe фонового потомка также означает omitted output. Supervisor затем
завершает группу и выдаёт cleanup receipt. Это не отмена уже выполненных эффектов
и не гарантия относительно намеренно отделившихся от группы внешних демонов.

`LocalShell`: local work/cwd/provenance/admission проверки, exclusive owner,
журнал до spawn, task/cancel/status/shutdown, metrics для будущего maintenance
wiring. `ManagedSessions.contains` читает происхождение без native attach.
Внутренние helper CLI-входы поддерживают frozen-архитектуру; build script
добавляет standalone источники как data. Frozen artifact пока не собран.

Новые проверки этапа: journal **23 passed**, shell/provenance/scanner **87 passed**,
helper/execution/journal/CLI/provenance **55 passed**. Реальные синтетические
процессы использованы только на Linux, в tmp_path, без модели.

Финальный набор этапа, включая scanner и ненаследование токенов: **99 passed**;
Ruff check/format (307 файлов) и diff check чистые. Gateway schema не менялась
относительно предыдущей части (12); shell journal имеет собственную БД.

## Control/runtime этап

Реализовано согласование X-ACP-Shell-Operations/Welcome, строгие ShellRequest/
Result/Response, отдельные relay RPC/worker квоты по 4, проверка epoch/request/
operation, отказ старого peer до отправки start. Start — control frame, никогда
не replayable ACP Data. LocalShell.request возвращает bounded status немедленно,
не ожидая окончания команды; вывод читается окнами по 4000 символов с offsets.
Reason — whitelist, сырые ошибки/команда/digest не становятся reason.

run_connector и commands runtime передают handler, сохраняют LocalShell между
сетевыми соединениями, учитывают её counters в maintenance и закрывают при
остановке коннектора. Старые незавершённые записи восстанавливаются до activity.
Проверки: **170 passed / 3 skipped** control/profile/maintenance/runtime/execution;
Linux local WS + синтетические команды, без моделей. Native Windows/WSL не заявлены.

## Требования этапа диспетчера и Telegram

- Записать UUID, owner/chat, исходный agent/computer/local alias/native SID/cwd,
  маскированную команду и dispatching **до network await**. После restart или
  unknown — только запрос status этого UUID, без автоматического нового start.
  Выбор другого диалога не меняет адресат команды/status/cancel.
- Можно использовать existing SQLite channel_state с атомарным multi-key helper
  (индекс + операция) вместо очередной миграции, если ownership/лимиты/retention
  и recovery сохраняются. Перед необратимой отправкой нужен core maintenance
  admission + счётчик in-flight control operations, чтобы snapshot не обрывал start.
- Полный stdout/stderr (ограничен PC) собрать из окон в памяти. Сопоставлять
  operation/state/exit/total на каждом окне, reject mismatch/пустое окно до конца.
  Маскировать полный текст **до** записи/рендера: зарегистрированный только
  на диспетчере секрет может пересечь границу окон. При обрыве fetch не сохранять
  сырой префикс и не пересылать его модели; повтор чтения не исполняет команду.
- Карточка результата имеет source/ПК/cwd/interpreter, status, exit/timeout/
  requested cancellation/unknown, страницы вывода, явное «Передать агенту».
  Card reference/purpose сохраняются, background делает edit только известной
  карточки; ambiguous send/edit не создаёт автоматический дубль.
- `!` обрабатывается после cwd/profile/name forms. Unsupported/refused не
  превращается в prompt агенту. На старом connector — понятная рекомендация
  обновления. Background не делает нового start и не передаёт вывод модели.
- Передача результата once-only, привязана к исходному диалогу и актуальной
  selection revision; если другая цель выбрана, сначала явное «Сделать активным».
  Sending→unknown после crash, не автоматический повтор модельного запроса.

## Dispatcher/Telegram — реализация и точка восстановления

`shell_dispatcher.py` использует SQLite `channel_state` диспетчера: namespace
бота, индекс `shell_operations` и записи `shell_operation:UUID`. Новый
`Store.set_channel_states` коммитит индекс+intent одной транзакцией до RPC.
Schema остаётся 12. Лимит 1000 записей; подтверждённые terminal записи старше
7 дней удаляются при admission новой команды, unknown сохраняются. Команда
маскируется до записи; сырые окна вывода собираются только в памяти, проверяются
по подписи результата и маскируются целиком до сохранения. Recovery переводит
dispatching/transfer sending/card sending в unknown и никогда не вызывает start.
Core считает in-flight control operations для admission обслуживания.

`telegram_shell.py` обрабатывает `!` после cwd/profile/rename форм, до обычной
отправки модели. Старый connector/direct backend получает явный отказ.
`/shells [page]` показывает операции владельца; `/shell UUID [page]` читает
результат. Status/cancel не меняют исходный ПК/диалог после переключения.
Карточка хранит исходный контекст, shell, статус/код/cleanup, страницы вывода
по 600 символов, текущий адресат текста, отдельную передачу агенту.
Карточка не является navigation panel: меню открывается отдельно. Редактирование
и изменения записи сериализуются тем же per-operation lock. Ambiguous send/edit
не порождает автоматический дубль; explicit повтор через `/shells` доступен.
429 считается явным отказом и позволяет последующий edit. Background ограничен
16 операциями за проход, unknown опрашивает реже, после restart перевязывает
кнопки известных сообщений. Он не запускает команду и не отправляет вывод модели.

«Передать агенту» требует исходный активный диалог и проверяет UI/active revision
ещё раз под core submit lock. Sending пишется до submit; после неоднозначного
сбоя только unknown, без повторной модельной отправки. Успешная передача хранит
ID задачи; дубли обращаются к ней. Переключение на исходный диалог — отдельное
явное действие с проверкой owner/native SID.

Первые проверки: **54 passed** dispatcher/Telegram shell/maintenance/inline UI;
после дополнения настоящим WS+Linux process сценарием: **13 passed** shell
dispatcher/Telegram. Проверено: commit до await, redaction секрета на границе
окон, status-only recovery, foreign owner, ambiguity/no automatic duplicates,
selection race и once-only transfer, формы ввода, source card/menu separation.
Широкая регрессия Telegram/core/storage: **373 passed** (session 99173).
Итог после retention/routing/rollback дополнений: **124 passed** shell
dispatcher/Telegram/protocol/journal/relay/executor/helpers/secrets (session
94888). Числа пересекаются; не суммировать. Промежуточный запуск с неверным
путём `test_secret_scanner.py` не собрал тесты, исправлен на `test_check_secrets.py`.
Ruff check после текущих правок чистый. Windows/frozen artifact/live Telegram
здесь не проверялись; никаких публикаций или изменений живой БД.

Перед Windows-реализацией проверены первичные источники Microsoft: обычные
CreateProcess-потомки наследуют Job, breakaway должен быть выключен; процесс
нужно включить в Job до исполнения пользовательской команды. Закрытие последнего
handle с KILL_ON_JOB_CLOSE инициирует завершение. Для доказательства cleanup
потребуется проверить accounting ActiveProcesses=0, а не только exit launcher.
Frozen PyInstaller bootstrap может создавать промежуточного потомка до attach:
нельзя считать assign только bootloader PID достаточным. Предпочтительны
приостановленный запуск с attach до resume либо handshake доверенного worker
с включением в Job до чтения command payload; job handle не должен оставаться
открытым в worker/потомках после handshake. Это пока дизайн, реализации нет.
Context7 tool в сессии недоступен; использован fallback на Microsoft Learn:
[AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject),
[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

## Native Windows — реализовано, native evidence ожидается

Реализация: `connectors/_windows_shell_job.py`, `windows_shell.py`, worker gate,
native ветка `shell_runner.py`, hidden CLI и build data. Выбран вариант
self-assignment доверенного worker в уникальный named Job до чтения payload.
Parent ждёт точный READY, worker до READY закрывает Job handle. Поэтому реальный
worker внутри frozen bootloader тоже входит в Job и не держит его handle живым
при смерти коннектора. KILL_ON_JOB_CLOSE и запрет breakaway установлены до spawn;
существующий named Job не принимается. Cleanup проверяет пустую accounting и
выход launcher, закрывает owned pipes; ошибка означает unknown.

PowerShell: абсолютный SystemRoot/System32 путь, NoProfile/NonInteractive,
EncodedCommand (UTF-16LE) с UTF-8 output. Environment — локальный allowlist,
без gateway/Telegram/agent credentials. Command/cwd/timeout/output policy та же.

Проверки: **62 passed / 7 skipped** orchestration/protocol/journal; **82 passed**
Linux executor/helper/relay/Telegram/dispatcher/secrets. Ruff **318 файлов**,
diff check чистые. Все семь skipped — native Windows, включая Win64 ABI.
Фактический Windows process/Job и настоящий frozen artifact здесь не запускались.
Набор для Windows: `tests/integration/test_windows_shell_execution.py`.
