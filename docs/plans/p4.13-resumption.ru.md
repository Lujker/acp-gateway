## 0. Решение владельца 2026-10-23 — читать первым

**Почему.** Владелец и внешний обзор хода P4.13 (Claude Code, 2026-10-23)
пришли к одному выводу: 22–23.10 почти всё время ушло на тестовую
инфраструктуру, повторные ревью и проверки. Isolation guard — около 1500 строк и
четыре цикла ревью. Из 27 падений на Windows закрыто одно, частично — три. Цель
P4.13 при этом не сдвинулась: Codex или Claude Code отвечает в Telegram на
реальной связке владельца. Найденные дефекты исправить, но без лишних кругов.
Общие правила объёма проверки, git и журнала — в [`.hermes.md`](../../.hermes.md).

### 0.1 Решения (ответы владельца на вопросы обзора)

1. **Ревью по риску.** Независимое ревью — только для production-кода
   безопасности, IPC и ACK/ACL; сейчас это ACK-1 и ACL-backend A. Один цикл
   исправления, потом эскалация. Правки только в тестах и документации — без
   ревью.
2. **23 оставшихся падения — сначала сравнить с `main`.** То, что падает и на
   `main`, — старый долг Windows-совместимости: записать списком, P4.13 он не
   блокирует. Падения, которых на `main` нет, — регрессии P4.13, их чинить в
   P4.13. Исключение: старый дефект, фактически ломающий выбранный живой
   сценарий или ведущий к потере данных, влияет на выпуск по наблюдаемому
   ущербу, а не только по происхождению тестового падения.
3. **Git.** Разрешены локальные WIP-коммиты в `feature/p4.13-codex-managed` и
   `push` этой ветки. Merge в `main`, теги, релиз, deploy — только с отдельного
   разрешения.
4. **Полный набор на Windows разрешено запускать локально на этом ПК**, риск
   владелец принял. Strict isolation runner и аудит каждого модуля перед запуском
   больше не обязательны. Ограничения «broad/full Windows-suite не разрешён» и
   «модуль только после аудита» из разделов 14–16 отменены.

### 0.2 Порядок работы

1. **Сохранить текущее состояние.** `ruff check`, `ruff format --check`, затем
   один WIP-коммит всего накопленного (tracked и untracked: adapters, tests,
   guides, docs) и `push` ветки. Перед коммитом проверить, что в индекс не
   попали `.env`, `config.yaml` и другие локальные секреты.
2. **ACK-1** (описание в 16.2). Pending-ответ хранить вместе с эффективными
   аргументами операции и исходным `expires`. Повторять публикацию только при
   точном совпадении; обработанный ID держать как tombstone. Тест RED→GREEN,
   тесты maintenance на Windows и WSL, одно ревью, коммит.
3. **ACL-backend A** (описание в 16.3) в `windows_acl.py` на `pywin32`.
   Policy, freshness 5s и клиентские бюджеты не меняются. Parity-тесты против
   текущего PowerShell SCRIPT, один замер времени до и после на Windows.
   Bounded verifier child — только если замер покажет, что без него нельзя.
   Одно ревью, коммит. После этого закрыть win-f04/f05/f06.
4. **Baseline.** Полный `pytest` на Windows для `main` (отдельный
   `git worktree` со своим venv) и для ветки, плюс полный прогон ветки в WSL.
   Разделить падения: есть и на `main` → долг; только на ветке → регрессия.
   Итог — короткий список в журнале. Если при прогоне видно, что тест реально
   меняет службы или задачи Task Scheduler, — остановиться и сообщить владельцу.
5. **Починить регрессии P4.13** из шага 4, коммиты.
6. **P4.13.1 — рабочий режим удалённой разработки** (решение владельца
   2026-10-23): два режима, «Безопасный» и «Рабочий» с native auto mode, плюс
   отмена хода и восстановление чата. План —
   [`p4.13-work-mode.ru.md`](p4.13-work-mode.ru.md).
7. **Живая приёмка на целевой схеме и релиз** — раздел 6 плана P4.13.1. Он
   заменяет большую матрицу раздела 6 этого файла: сначала одна связка, в
   рабочем режиме. Отдельных стендов нет: коннектор этого ПК переводится на
   установку из checkout, личный диспетчер обновляется до rc. Перед стартом
   одним сообщением спросить владельца о модельном бюджете и подтверждении
   захода.

## 4. Найденные и исправленные дефекты

- Codex file approval первоначально не содержал достаточных path/kind/diff — исправлены retained item mapping и fail-closed cases.
- Codex shutdown зависел от descendant EOF — теперь собственные pipe transports закрываются явно; чужие процессы не убиваются.
- Claude assistant frame с top-level native `error` мог выдать diagnostic text как ответ. Исправлено fail-closed до content publication/deduplication.
- Claude queued approval удалял pending authority до получения child write lock. Native revocation в этом промежутке терялся. Исправлено: pending остаётся revocable до финальной проверки exact identity/child/session/current turn/done/closed под write lock, затем consume/write без await.
- Для двух Claude случаев сначала получены **8 ожидаемых RED failures**, затем GREEN и повторное независимое ревью. Уже отправленный native decision отозвать невозможно; это не безопасная отмена выполнения инструмента.

Неблокирующее улучшение тестов: сделать постоянными review probes для duplicate human responses, close до очистки permissions, error frame с уже completed message ID; отдельно проверить repeated tool_use_id под разными native request IDs. Это не новая активная очередь и не повод менять протокол без воспроизводимого дефекта.

## 5. Ограничения и незакрытые решения

- **Codex Windows helper:** `git.exe` иногда удерживает рабочий каталог после завершения App Server. Родитель воспроизвёл 4/5; каталог освобождался самостоятельно примерно через 1.75–1.84s. Graceful EOF 300ms не устранил lock. Не вносить произвольный sleep/process-tree kill как доказанное исправление. Owned stdio cleanup и helper lifecycle — разные проверки.
- Codex conservative default — `read-only`, `workspace-write` только явно. Native policy может разрешать действия без нового approval; не обещать gateway prompt на каждое действие.
- Claude `manual` сам по себе разрешает часть reads; adapter задаёт явные ask rules Read/Glob/Grep/Edit/Write/Bash и ограниченный tool surface. Это **не OS sandbox**, не безусловная гарантия перехвата любого native internal tool. Не добавлены bypass/always grants, arbitrary MCP/background agents.
- Claude использует **`--no-session-persistence`**: managed handles не образуют сохранённую native историю. Для future chat list/attach это нужно проектировать отдельно, а не просто включить discovery и заявить resume.
- Для обоих managed adapters нет arbitrary load/cold resume, replay после unknown, безопасного native-turn cancellation и управления тем же открытым Desktop-чатом. Cleanup транспорта не доказывает остановку всех потомков или отмену побочного эффекта.
- Desktop означает отдельный непроверенный режим: ещё требуется уточнить охват официальных Codex/Claude Desktop и техническую возможность наблюдения/согласованного исполнения с несколькими источниками/approval resolution. Не использовать ввод в чужой терминал, запись в native chat DB, копирование credentials или обход ACL как молчаливую замену интеграции.

## 10. Решения продуктовой прожарки 2026-10-22

**Состояние:** продуктовые требования ниже подтверждены владельцем; техническая реализуемость shared native chat ещё исследуется. Этот раздел уточняет будущую цель P4.13/P2.7, не объявляет её реализованной и не меняет очередь в конце road-map. Кодовый snapshot и результаты тестов 2026-10-21 остаются прежними.

### Подтверждённые решения

1. **Несколько равноправных источников одного чата.** Читать, писать и отвечать на approvals можно из CLI/Desktop, Telegram и VK без обязательного ручного переключения управляющего интерфейса. Это один исходный native чат и согласованное исполнение, а не несколько независимых процессов с копиями истории. Занятый чат сам по себе не причина запрещать подключение: решение вмешаться в работу остаётся пользователю.
2. **Поведение занятого чата — native.** Повторять поведение родного агента и показывать фактический исход: принятие в текущую задачу, native queue, отказ или unknown. Свою скрытую очередь не создавать; не изображать поддержку steering/queue там, где backend её не подтвердил. Пользователь отвечает за смысл своего вмешательства; система — за достоверный результат доставки, отсутствие скрытой подмены сессии и недопустимого replay.
3. **Список — весь выбранный локальный профиль.** Показывать все доступные чаты выбранного профиля агента на выбранном компьютере, не только gateway-created handles и не только один cwd. Это не разрешение читать чужие профили/аккаунты и не отмена существующего контроля доступа к коннектору.
4. **Привязка и явное resume после перезапуска.** Сохранять identity исходного чата и давать явно возобновить его после перезапуска, когда native контракт позволяет. Не повторять автоматически запрос с неизвестным результатом. Если восстановление не подтверждено — показать ограничение; новый чат не считать успешным resume. Текущие managed adapters, особенно Claude с no-session-persistence, этот контракт не обеспечивают.
5. **Native permissions существующего чата сохраняются.** Не ужесточать/ослаблять режим при attach незаметно; показывать действующий режим либо честное unknown. Изменение — только явно. Это не поручение ослаблять safe defaults новых managed-сессий. Если native policy не спрашивает approval, нельзя обещать дополнительный запрос только из-за Telegram/VK.
6. **Контекст при attach.** Карточка состояния плюс последние реальные сообщения; прочая доступная история — по запросу. Не выгружать всю историю автоматически и не создавать платное model-generated резюме для списка/preview.
7. **Уведомления — по подписке.** Новые события и результаты, включая задачи, начатые из Desktop, приходят только по явно выбранным/подписанным чатам; подписку можно отключить. Discovery списка сам по себе не подписывает на все чаты профиля.
8. **Telegram/VK — равноправные входы одного диспетчера.** Общие диалоги/задачи, без ручного переключателя между каналами; конфликтующие действия координируются, одно подтверждение принимается один раз. Native исполнитель остаётся источником факта, какое решение принято. Запоздалый deny не отменяет уже принятое allow; не объявлять победителя только по локальному порядку получения Telegram callback, если Desktop мог ответить раньше.
9. **Первый VK scope.** Выбор компьютера/агента/диалога, текст/код, результаты и human approvals — полезный законченный рабочий цикл. Администрирование/обновления не обязательны для первого подэтапа; загрузка файлов/изображений — отдельный последующий подэтап. Это уточнение порядка возможностей, не отмена общего долгосрочного scope VK.

### Какие прежние решения отменены

В первом раунде владелец согласился с предложением поочерёдного управления и явной передачи между Desktop и диспетчером, а также с ожиданием завершения turn. После разбора случая pending approval поставил под сомнение необходимость запрета и явно выбрал одновременные источники.

**SUPERSEDED:** обязательная ручная передача управляющего интерфейса; запрет подключаться/писать в busy chat до завершения turn; отдельное исключение «передавать контроль на остановленном approval». Их заменяет единый multi-source контракт выше. Не возвращать эти ограничения как уже согласованное требование. При этом точно один native action/решение и отсутствие replay не отменены; невозможность конкретного backend может быть фактом, но не продуктовым решением пользователя.

### Что остаётся нерешённым

- **Q2 / DECISION после технической матрицы:** можно ли выпускать доступные режимы, если один агент/платформа не обеспечит полноценный shared Desktop attach, или это блокирует полезность ближайшего этапа. **Ответ владельца 2026-10-23: да** — доступные режимы (список и продолжение закрытых чатов, 4a) выпускаются, не дожидаясь живого общего подключения (4b); см. очередь road-map.
- Охват Hermes для native list/attach явно не подтверждён; не расширять на него автоматически требования Codex/Claude.
- Числа для объёма preview, pagination, retention, лимитов native discovery/подписок, модельного/денежного бюджета и сроков не выбирались. Параметры нужны перед соответствующим изменением или расходом; не придумывать их как одобренные.
- Последовательность новых сообщений и поддержка вмешательства в active turn определяются фактическим native API. Исследование не вправе молча заменить это собственным планировщиком либо второй native сессией.

### Следующий исследовательский артефакт перед реализацией list/shared attach

Нужна versioned capability matrix для Codex/Claude CLI/Desktop на реальных применимых окружениях Windows/WSL. Для каждой ячейки различать **DOCUMENTED**, **PROBED**, **LIVE ACCEPTED**, **UNSUPPORTED**, **UNKNOWN**; не закрывать несколько уровней одним зелёным значком. Не предполагать наличие Desktop-приложения внутри WSL только из-за работающего CLI.

Проверить раздельно:

- discover/list и stable identity профиля/чата, чтение метаданных/истории без model turn и без других аккаунтов;
- observe существующего idle/busy native процесса, подключение второго клиента без смены исполнителя;
- отправку во время active turn с native semantics и понятным ack/unknown;
- approvals из нескольких поверхностей: allow/deny race, resolved/withdrawn, stale UI и отсутствие второго действия;
- loss/reconnect/restart с сохранённой привязкой и явным resume без replay неизвестного запроса;
- неизменность native permission settings при attach;
- подписки на выбранные чаты без рассылки остальной истории;
- ограничения real native auth/OS/transport, поддержанный отказ там, где контракт не подтверждён.

Результат исследования — конкретный поддерживаемый механизм и воспроизводимые проверки/ограничения по backend, затем решение владельца Q2 о допустимости частичного выпуска. Модельные пробы, установка/активация новых channels/plugins, изменения local settings, аккаунтов или production требуют отдельного поручения. Прожарка этого не разрешает. ## 11. Смешанный Windows/WSL и отдельные среды — требование 2026-10-22

**Подтверждённая цель владельца:** поддерживать его реальную топологию — коннектор на Windows 10, Codex/Claude Code установлены и работают в WSL, Desktop-приложения ChatGPT/Claude находятся на Windows. Аналогичная топология есть на рабочем ПК по сообщению владельца; удалённо она не обследовалась. Корректно отличать её от чистого Linux, macOS и native Windows без WSL. Это требование к дальнейшему P4.13, не объявление уже работающего mixed режима и не поручение устанавливать/перенастраивать ПО.

### Фактическое состояние кода и документации

- `CodexSettings`/`ClaudeCodeSettings` задают CLI executable, но не WSL distribution/user/execution environment. `CodexAcpTransport.open` и `ClaudeCodeAcpTransport._spawn_owned` вызывают `asyncio.create_subprocess_exec` с native executable/фиксированными flags и cwd окружения самого коннектора. First-class Windows connector → WSL launcher/bridge/discovery пока нет.
- Существующие проверки коннектора/адаптера внутри WSL и native Windows checks — разные same-environment проверки. Они **не доказывают** Windows connector → WSL agent. Простая замена executable на `wsl.exe` без параметров среды, argv/cwd/auth/lifecycle mapping не является поддержанным решением.
- Same-environment путь с отдельным коннектором рядом с CLI внутри WSL архитектурно доступен как кандидат существующей инфраструктуры, но для новых Codex/Claude тоже требует живой приёмки. Это не выполненное требование одного Windows-коннектора; не навязывать второй pairing/ручной перенос секретов как единственную архитектуру.
- GUI location не определяет execution environment. По первичным официальным страницам, прочитанным 2026-10-22: OpenAI Desktop Windows может запускать Codex native или WSL2; Claude Desktop Code также имеет WSL2 environment. Это возможности upstream, не доказательство доступности/работы их API в установленном build.

### Целевая модель — ещё не схема текущего конфига

Различать **physical computer → execution environment → agent installation/profile → native runtime/chat → connected UI surfaces**.

- У одного ПК есть native среда и ноль/несколько явно выбранных WSL-дистрибутивов. WSL distribution, Linux user, профиль/home и executable — часть адресуемой среды, а не случайный текущий default. Windows user/service identity запуска коннектора также существенна.
- Установка агента имеет собственные kind/version/profile/home/capabilities. Native ID связывается как минимум с computer/environment/agent/profile, а live execution — с instance/epoch. Одинаковая строка chat ID или одинаковый cwd в двух средах не доказывают один чат.
- CLI/Desktop — поверхности доступа, не автоматически две разные установки или один общий runtime. Windows GUI может обслуживать WSL runtime. Один подтверждённый runtime/chat показывать согласованно, а не клонировать из-за двух UI. При отсутствии доказанного общего runtime не склеивать чаты.
- Общий filesystem/home/config, если владелец уже настроил sharing, учитывать по фактическим настройкам; наличие общих файлов не доказывает общий live процесс. Не копировать и не синхронизировать Windows/WSL credentials/историю автоматически, не менять CODEX_HOME/Claude config и login ради discovery.
- Путь хранить и проверять в его среде: Windows path, Linux path и UNC view не взаимозаменяемы без явного mapping. `/mnt/c/...` остаётся Linux-путём WSL исполнения. Проверки cwd/permissions должны исполняться на нужной стороне границы.
- В интерфейсе сохранять простой выбор компьютера/агента, но показывать badge среды: например, `Codex · WSL/Ubuntu-22.04` или `Claude Code · Windows`. Не требовать считать каждую среду отдельным физическим компьютером. Названия — примеры будущего UI, не зарегистрированные маршруты.

### Архитектурный кандидат, а не уже выбранная реализация

Предпочтительный для исследования UX — один зарегистрированный Windows-коннектор публикует native и явно разрешённые WSL agents. Для WSL можно использовать local runner/bridge через документированный launcher/IPC. Нужна проверка, достаточно ли прямого stdio запуска либо нужен Linux-side helper для lifecycle/attach. Не обещать, что одна команда `wsl.exe` сама решает live Desktop attach, approvals и reconnect. Второй публичный listener/перенос model credentials на диспетчер не является требованием.

Discovery дистрибутивов не должно запускать все среды или менять default distro/user. Если нужная среда остановлена, недоступна, агент отсутствует или policy не позволяет запуск — показать конкретное состояние и разрешённое явное действие, а не молча переключаться на Windows agent, другую distro или root. Проверить реальные permissions Windows login/service context; не компенсировать отсутствие доступа повышением привилегий.

### Раздельная матрица целевой поддержки

| Коннектор / управляющая сторона | Исполнение агента | Текущий уровень evidence |
| --- | --- | --- |
| Native Windows | Native Windows | Managed код + synthetic peer/config tests; live не принят |
| Внутри WSL | Та же выбранная WSL environment | Managed код + WSL tests/initialize-only; live не принят |
| **Windows 10 host connector** | **Явная WSL distribution/user** | **Новый обязательный сценарий; bridge не реализован/не принят** |
| Native Linux без WSL | Native Linux | Целевая поддержка; WSL evidence не заменяет bare-Linux acceptance |
| Native macOS | Native macOS | Целевая поддержка; на macOS не проверено, приёмка владельцем позднее |

Для каждой ячейки отдельно вести managed new chat, native catalogue/history, stored resume и same-runtime live attach; Windows Desktop → WSL runtime — отдельная проверка UI/исполнения поверх mixed режима. Четыре колонки раздела 6 не закрывают mixed или macOS/bare-Linux ячейки. Массовую проверку всех платформ не запускать параллельно: сохраняется один активный пункт и проверяемые подэтапы. Новая цель не делает macOS немедленным blocker и не переставляет очередь native list/attach → VK.

Версии Windows/WSL/дистрибутива, WSL generation, CLI/runtime/Desktop и архитектуру фиксировать раздельно. Не обещать WSL1: текущая документация OpenAI указывает отсутствие WSL1 поддержки Codex начиная с 0.115. Совместимость конкретного Windows 10 build/WSL/upstream приложения проверяется отдельно; не объявлять поддержку, если upstream контракт или установленный build её не обеспечивает. Q2 о допустимости частичного выпуска остаётся открытым до конкретной матрицы.

### Обязательные mixed acceptance cases

1. Точно выбрать distro/user/profile/executable; несколько distro, другой default, разные logins и одинаковые native ID не приводят к cross-routing.
2. Безмодельная проверка version/initialize из Windows через предполагаемый WSL transport: правильные argv/cwd/env, UTF-8/JSONL и чистые protocol stdout; Linux auth остаётся на своей стороне. Затем отдельно разрешённые model/Telegram trials.
3. Получить список/историю только нужной среды и подтвердить exact original chat/runtime перед записью. Сохранённые transcript, общий config store и live attach не смешивать.
4. Busy input и allow/deny из Windows Desktop/мессенджеров разрешаются с native semantics и exact environment/session/turn/request binding; старые UI actions отклоняются после смены instance/epoch.
5. Потеря Windows wrapper, Linux runner/agent, link, sleep/restart/WSL stop дают корректный known/unknown outcome без replay/нового чата. Закрытие `wsl.exe` не считать доказательством завершения Linux child. Не применять `wsl --shutdown`, termination всей distro или широкое убийство процессов ради cleanup одного owned turn.
6. Subscription/preview/permissions и безопасные managed defaults сохраняют контракт раздела 10 независимо от placement UI/коннектора/исполнителя.
