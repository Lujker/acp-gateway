## Локальное shell-исполнение — новый подтверждённый этап

Добавлены `connectors/shell_journal.py`, `shell_runner.py`, `shell_service.py`,
standalone `_shell_worker.py`. `ManagedSessions.contains` проверяет provenance
без подключения модели и без снятия busy-fence. LocalShell требует локальный
managed work-профиль, разрешённую cwd, известную этому профилю сессию и admission;
имеет exclusive FileLock и отдельный SQLite-журнал, учитывает активность/uncertainty.
Safe/чужая сессия/иная cwd отклоняются до reserve/spawn. Новый UUID фиксируется
до исполнения; дубликаты, восстановление и истечение результата не запускают команду.
Tombstones сохраняются (100000 идентификаторов), содержимое ограничено 1024
неистёкшими результатами; вывод/команда истекают через 7 дней, неопределённая
очистка не удаляется автоматически. Одновременно до 4 операций, timeout до 600 с.

Linux использует существующий `_wsl_runner` и его receipt очистки группы:
родитель не наследует gateway-токены в shell. Worker запускает sh с DEVNULL
stdin, дренирует stdout/stderr с общим пределом 60000 байт. Переполнение или
зависшие у потомка pipes приводят к пропуску вывода целиком, без сырого префикса
секрета. Маскирование до сохранения статуса. Отмена/таймаут завершаются только
после проверки supervisor cleanup; исключение runner даёт unknown, а не fake success.
WSL-ветка использует этот же worker через `spawn_wsl`, но живой Windows→WSL
прогон не выполнен. Native Windows/Mac сейчас **не поддержаны** этим runner.

Добавлены внутренние CLI-входы `__shell-worker`/`__shell-supervisor` для frozen
бинарника без загрузки конфига. Пакетный build включает оба standalone .py
ресурса явно; сам бинарник на этом этапе не собирался. Проверка helper CLI
через Python успешна, не равна evidence frozen/native Windows.

## Shell control protocol и runtime — подтверждённый этап

В `protocol.py` добавлены ShellRequest/Result/Response: start требует точный
alias/session/cwd/command, status/cancel не принимают execution payload; actor,
expiry, timeout, output offset, enum reasons и cleanup/exit invariants проверяются.
Result содержит окно до 4000 символов (общий вывод до 65536), не раскрывает
digest/raw-command/cwd локального журнала. Проверен worst-case JSON control-frame
budget и запрет success без receipt. Расширение X-ACP-Shell-Operations/Welcome
согласуется отдельно; старые peers отказывают до выполнения.

`RelayPeer` имеет отдельные pending RPC/worker квоты по 4, epoch/request/operation
binding, cleanup futures при разрыве и typed result. Shell start не помещается
в resumable ACP Data, не открывает модельные streams. RPC только ставит работу
в LocalShell; потеря WS не отменяет/не повторяет уже принятую команду. Диспетчер
проверяет регистрацию до и после ответа; alias start должен быть объявлен ПК.

`commands.py` подключает LocalShell к run_connector, закрывает при shutdown,
восстанавливает старый shell journal до публикации activity (даже если профиль
удалён). Для нового профиля service может создаться лениво. `ConnectorMaintenance`
складывает отдельные service counters и отказывает на невалидных counters;
активные shell и неизвестная очистка входят в preflight и запрещают обычную
reservation/profile edit/update. Существующий explicit restart_uncertain сохранён.

Проверки новых protocol + real WS сценариев — **26 passed**; широкий
control/profile/maintenance/commands/execution/protocol regression —
**170 passed / 3 skipped** (session **19324**). Пропуски — native ACL сценарии,
не evidence Windows. Проверены реальный run_connector reconnect loop,
потеря start response + reconnect/status + тот же UUID (файл изменён ровно один раз),
изоляция квоты от updater inventory, stale/foreign/неверные epoch и operation,
большой вывод и redaction до границ его сетевых окон.

Последняя небольшая правка добавляет явный отказ unmanaged-профиля до runner;
её финальные проверки указать после получения результата следующего прогона.
**Точный следующий шаг:** persistence диспетчера **до** ShellRequest start,
recovery только через status (никакого start replay), затем Telegram `!` после
форм ввода, обновляемая карточка/status/cancel и once-only «Передать агенту».
Для вывода сначала собрать весь ограниченный результат в памяти и маскировать
до сохранения/показа: PC может не знать зарегистрированный секрет диспетчера,
а такой секрет может пересечь границу окна 4000 символов. Не публиковать и не
хранить в SQLite сырой partial prefix. Структурный план UI — в shell-документе.

## 2026-10-27 — native Windows shell executor

Добавлены `_windows_shell_job.py` (stdlib-only Win32 API), `windows_shell.py`

На операцию создаётся новый Job Object с 256-bit именем в Local namespace,
KILL_ON_JOB_CLOSE и без breakaway. Существующий объект/неприменённые limits —

ошибка/отмена до gate не исполняет команду.

ActiveProcesses=0 и выход launcher, закрывает Job и Proactor pipes; неполное
доказательство сохраняет unknown. Это управление обычными потомками CreateProcess,
